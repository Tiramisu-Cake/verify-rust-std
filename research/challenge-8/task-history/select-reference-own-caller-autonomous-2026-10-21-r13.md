## Ближайшая proof-цель и порядок работы

**Главная цель — проверенное тело generic Option<&T> cleanup helper в существующей модели, затем P0c с собственным receipt и native P1.** Сам выбирай конкретные исправления и эксперименты по плану; порядок ниже задаёт зависимости и предотвращает повтор дорогой полной кампании с известным blocker.

1. **Разбери ресурсный blocker и минимальную гипотезу до Cloud.** Используй уже установленную source chain, не повторяй grammar audit без нового дефекта. Opening generic Option_own оставляет opaque shared-reference own; имеющийся `close_ref_own` имеет направление share→own, обратное из него не следует. Исследуй checked proof либо сохраняющую представление нормализацию enum-field type predicate через существующую RustBelt интерпретацию. До реализации запиши source applicability, соответствие двух представлений, сохраняемые ресурсы/постусловия и различающие controls. Не предписывается конкретная реализация; новая непроверенная own↔share аксиома/обратная lemma недопустима. Если без нового доверенного допущения путь невозможен, укажи точный недостающий факт и продолжай независимые задачи в scope.
2. **Первый полезный proof experiment — минимальный faithful helper probe.** Он должен проверять тот же проблемный ресурс и generic arbitrary None/Some, без предположений None/Emp, Copy/Freeze для T или потери поля Some. В изменённой репрезентации различи shared-reference и non-reference поля, generic type/lifetime substitution, оба constructor и сохранение требуемых normal/unwind ресурсов там, где они применимы. Используй существующий pinned source/compile preflight и сразу target со связанными controls; отдельный compile-only Build — лишь при измеримой экономии. Actual parser/compiler/verifier только Cloud. Mini-helper PASS — промежуточное evidence, не receipt canonical caller.
3. **Перед очередной длинной кампанией устрани потерю частичных результатов.** Найди фактический уровень deadline/timeout в S3/S4 через точные stage records и адресные Brief queries. Сначала проверь существующий persist_progress/partial audit: сохраняется ли результат и попадает ли в пакет при timeout/exception/termination. Минимально исправь producer/consumer: атомарный компактный snapshot после завершённого case/stage, точные source/tool/profile/Build IDs, последняя наблюдённая стадия и причина пропуска только при наличии records. Проверь success/error/timeout/partial/missing/null/wrong-type и error-path упаковки; при жёстком kill может сохраниться только последний завершённый snapshot, не обещай полный отчёт.
