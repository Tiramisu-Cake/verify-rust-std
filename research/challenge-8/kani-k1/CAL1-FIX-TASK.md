## Правки

1. **Восстанови feature gate.** Добавь в `library/core/src/lib.rs` атрибут `#![cfg_attr(all(kani, kani_smallsort_cal1), feature(fn_traits))]`. Сохрани существующие `KeyLess<u8>`, домены и тела проверок. В `check_overlay_layout` разреши только эту дополнительную строку в `core/src/lib.rs` и проверь, что её удаление восстанавливает blob базы побайтно. Пересобери локальные Git-объекты и bundle так, чтобы новый overlay имел единственным parent `dab03cf510`. Сверь SHA/tree, bundle и frozen request, подготовь только новый локальный control. Если следующий приём даст другую первичную ошибку, она должна стать отдельным наблюдением с координатами.
2. **Сохрани начало диагностики в setup receipt.** На пине `run_build` читает JSON-сообщения Cargo и печатает раскрытые ошибки rustc в **stdout**. Сейчас `list_one` берёт только последние 4096 байт `stderr.log`. В failure path для tool build, compile gate и обоих discovery сохраняй отдельные bounded записи для stdout и stderr. По каждому потоку удерживай первые 80 строк с первой диагностики уровня error, максимум 16 KiB на поток. Включи заголовок и код ошибки, файл/строку, разметку, первые note/help, сохраняй порядок. Учти ANSI-разметку. Если распознаваемого заголовка нет, оставь небольшой префикс с пометкой о fallback. Хвост Cargo сохраняй отдельным полем для итогового количества. Укажи исходный поток, координаты, объём просмотренных данных и усечение. Читай по имеющемуся ограниченному захвату или в потоке, без публикации сырых логов и увеличения их капов. [Вывод ошибок Kani](https://github.com/model-checking/kani/blob/9834c96ce90ff57d8495416530b080dc3d52ce25/kani-driver/src/call_cargo.rs#L310-L341) · [Печать в stdout](https://github.com/model-checking/kani/blob/9834c96ce90ff57d8495416530b080dc3d52ce25/kani-driver/src/call_cargo.rs#L515-L522) · [Текущий excerpt](/root/kani-cal1-control-w11/ch8-cal1/run.py:129)
3. **Остановись на ошибке cfg-on до base discovery.** После установки и аттестации stock Kani материализуй точный overlay и запусти короткую фазу `OVERLAY_COMPILE_PREFLIGHT` с тем же `std/library`, cfg on, pinned Kani, общими флагами и отдельным свежим target. Предпочтительный вызов — `kani verify-std` с `-Z unstable-options --no-codegen --only-codegen`, без `--export-json`. По исходнику пина свяжи `--no-codegen` с флагом rustc и проверь, что `--only-codegen` останавливает driver после `std_project`, до запуска проверок. Верхнее окно — 180 с внутри прежнего setup-дедлайна, с watchdog и reap. Подтверди в receipt запуск компиляции с нужным cfg, exit 0 и отсутствие verifier children. Это проверка компиляции всей cfg-on `core` без зачёта корней. Если путь compile-only на данном пине технически неприменим, вынеси **точный overlay `kani list --std`** вперёд и переиспользуй его успешный результат. Он улавливает исходный compile failure до base без второго полного overlay list, но успешный полный list может оставаться дорогим. В handoff обоснуй выбранный путь и укажи его пределы. [Флаги driver](https://github.com/model-checking/kani/blob/9834c96ce90ff57d8495416530b080dc3d52ce25/kani-driver/src/call_single_file.rs#L201-L230) · [Остановка до проверки](https://github.com/model-checking/kani/blob/9834c96ce90ff57d8495416530b080dc3d52ce25/kani-driver/src/main.rs#L149-L175)

При неуспехе gate запиши `SETUP_ERROR` с точной фазой, argv, cfg, exit code или причиной cutoff, таймингом, RSS и первыми диагностиками в `setup.json`. В `error.json` оставь ссылку на запись и короткое первичное сообщение, если оно распознано. Общий статус child `EXITED` сам по себе недостаточен. При timeout/RSS статус компиляции остаётся неизвестным. Base discovery, слоты и macOS после общего Linux setup failure не стартуют. `always()` сохраняет частичный артефакт. После успешной короткой пробы нужен полный cfg-on discovery для сверки exact selector/kind, а также cfg-off base inventory для партиций. Выполни точный cfg-on discovery перед длинным base list, затем верни detached overlay для замеров. При запасном пути compile gate и полное cfg-on discovery — один вызов.

## Валидация и границы

- Сохрани 11 корней, OB12, solver, свойства, covers, среды Linux/macOS, окна слотов, RSS guards и отдельное окно аттестации и upload. У короткого gate свой дедлайн внутри setup. Синтетические сценарии должны доказывать, что ошибка ранней пробы и ошибка полного cfg-on discovery не вызывают base list. Успешный сценарий сверяет оба списка и возвращает точный overlay. Проверить, что отчёт не отмечает виртуальные результаты у `NOT_RUN` и что `common_ready` появляется после обязательного discovery.
- Добавь синтетический failure case с первичной `error[E0183]` в stdout, продолжением на нескольких строках и большим каскадом сообщений. В stderr оставь Cargo summary. Проверь удержание первой диагностики, source span, отдельный tail, размеры/флаги усечения и публикацию при выходе с кодом 1. Проверь также ошибку в stderr и timeout без первичной ошибки. Для layout guard проверь восстановление base blob и отказ на второй несогласованной правке. Переиспользуй тесты runner и проверки trigger из CAL1.
- В handoff перечисли изменённые файлы, старые и новые SHA/tree/parent, SHA-256 request и bundle, выбранный argv ранней пробы, фазовый порядок и тестовые результаты. Независимый ревьюер сверяет перенос feature, guard, сохранение первых ошибок, порядок и часы, чистый пин, unchanged measurement semantics и точную привязку будущего trigger. Фактический compile PASS с исправлением остаётся критерием будущего hosted запуска.
