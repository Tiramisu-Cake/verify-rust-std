# SCOPE — какие доказательства остаются в ordinary, какие уходят в opt-in (бюджет CI)

Дата: 2026-10-29. Исполнитель: Codex, одна сессия, окно до 3 ч. Worktree `/root/verify-rust-std-kani-scope`, ветка
`experiment/kani-k1-scope-20261029` (от `6ce4c84d` = итог C3c). **Сборок нет** (Cloud Build, Actions, CircleCI —
не запускать). Ветку подачи `submission/ch8-smallsort-min-20261028` не трогать.

## Зачем

Владелец решил: тяжёлые доказательства SmallSort выносятся из ordinary-набора в opt-in, чтобы пакет проходил
все проверки организаторов (job `kani_autoharness`: все ручные гармоники на одном раннере, 3 потока, 10 мин на
гармонику; ubuntu-раннер на прежнем наборе умер). Ориентир организаторов для Ch8 (issue #56, qinheping,
2025-01-24): «ideally the running time of a single proof should be less than ~2 minutes on a GitHub standard
runner. However, if the proof is running into the limitation of Kani/CBMC, we suggest you to open a PR with the
proof so that we could merge it once we have made performance improvements». Это пересмотр минимального плана,
а не только описания CI — поэтому нужна таблица решений с зависимостями.

## Правки по обсуждению с планировщиком (обязательны, имеют приоритет над текстом ниже)

1. **Основание доказанности по SHA.** П-6 (8/8 партиций) относится к `6cfc76cb`, не ко всему `e9655515`: C3a-гармоники
   имеют отдельные результаты (RESULT-C3A). В таблице для каждой гармоники — источник свидетельства и его SHA
   (историческая партиция / autoharness / GCB-замер). Без сборок итог SCOPE — **предложенный состав, пригодность
   для CI не проверена**; так и назвать в документе.
2. **Бюджет.** «Сумма VT ≤ ≈1 ч» — наша рабочая цель, не критерий организаторов и не граница wall job. Добавить
   память (известные пики) и число одновременно тяжёлых проверок. Для C3a подходящей калибровочной группы нет —
   **UNKNOWN**, не подставлять r другой семьи. Неизмеренное время не считать нулём: сумма известных + отдельно
   неизвестный остаток.
3. **Порядок отбора:** (а) сохранить ценные свойства вместе с необходимыми callee; (б) убрать дорогие дубли;
   (в) верхние домены рассматривать целыми группами зависимостей. Ordinary `proof_for_contract` сам по себе не
   закрывает уже раскрытые переносы между аллокациями. Контроли с ожидаемым FAILED остаются opt-in; в ordinary
   могут оставаться только положительные свидетели.
4. **Разбиения C3c** переносить вместе с нужными helper-макросами, но без невыбранных E/K. Замеры C3c относятся к
   сочетанию с E/K: после восстановления covers или смены solver время разбиения не подтверждено — помечать
   «требует замера». Если у исходной гармоники был TIMEOUT, «не раздувает сумму» не установлено.
5. **E** — не в основном патче (меняет тела проверок, а этап разрешает только `cfg` на уровне item). Описать
   отдельной опцией с необходимым повторным covers-аудитом.
6. **Механизм opt-in** — существующий `cfg(kani_smallsort_controls)` с отдельными манифестами: положительные
   расширенные проверки (ожидание PASS) и контроли (ожидание FAILED). Команды воспроизведения выбирают список явно.
   Новый cfg `kani_smallsort_extended` не вводить (lane его не поддерживает; это отдельная инфраструктурная работа).
7. **Inventory:** карта «исходная гармоника → преемники → объединение доменов» (а не сохранение каждого имени);
   явно указать, остаётся ли исходная гармоника дополнительно в opt-in. Python-проверку называть статическим
   прогнозом: она не заменяет раскрытие макросов компилятором и `kani list`.
8. **План проверки** дополнить: обе конфигурации с раздельными ожиданиями PASS/FAILED; фактический inventory;
   полные ordinary-партиции и autoharness на Linux и macOS (раскладка партиций меняется с числом гармоник); аудит
   перенесённых covers и зависимых контрактов.

## Что сделать

1. **Таблица всех ordinary пакета** `research/challenge-8/kani-k1/scope/scope.tsv`: имя; семейство; свойство
   (safety / sorted+permutation / контракт X / route / drop / …); домен (тип, длины, маршрут, тело из шести);
   зависимости (`stub_verified` → какой `proof_for_contract` и его домен; используемые контракты); время macOS
   (источник: П-6 mac / прогноз из GCB с группой r / TIMEOUT); решение `ordinary` / `opt-in`; основание.
2. **Принцип выбора** (согласован с планировщиком): сначала полезность и зависимости, затем стоимость.
   - Ориентир — ≤ 120 с на macOS на гармонику (с учётом, что в job 3 потока); учитывать также сумму семейства и
     общую долю в job. Цель для ordinary SmallSort — сумма Verification Time на macOS **не больше ≈ 1 ч** и ни одной
     гармоники > 300 с; если цель недостижима без потери важных доменов — показать варианты.
   - В первую очередь сохранять: реальные trait-входы, точки смены алгоритма, максимальные длины safety (если
     укладываются), отрицательные/контрольные свойства, уже лёгкие гармоники. Первые кандидаты на вынос — дорогие
     дубли свойств и верхние длины дорогих семейств.
   - **Нельзя** оставить ordinary-claim, опирающийся на `stub_verified`, если соответствующее доказательство
     контракта уходит в opt-in (пример: merge u64 N16 — предпосылка general/stable N16). Тогда либо оставить
     доказательство того же домена, либо вынести/переобозначить зависимые результаты. Аналогично регионы
     insert_tail, типы, компараторы, аллокации.
   - Разбиения C3c брать только там, где они измерены как полезные (все части SUCCESS в GCB с запасом) и не
     раздувают сумму; иначе — исходная гармоника в ordinary или в opt-in.
   - Covers: по умолчанию **оставить политику пакета** (covers в ordinary, без варианта E). E применять только
     если без него не выполняется бюджет — с обоснованием.
3. **Решающая таблица для владельца** `scope/SCOPE.md` (русский): ≤ 25 строк по семействам, где есть решение
   (что остаётся / что уходит / зависимости / стоимость до→после / что теряет заявление PR) + одна строка
   «остальные N без изменений». Итоговый прогноз ordinary SmallSort: число гармоник, сумма и max VT macOS,
   число > 120 с, с источником каждой цифры. Черновик английского текста для PR: абзац про opt-in (≤ 6 строк) со
   ссылкой на #56 и списком вынесенных доменов (≤ 1 строка на семейство).
4. **Патч** на эту ветку (отдельный library-коммит от e9655515-библиотеки: сначала коммит, восстанавливающий
   `library/` ровно к e9655515, затем изменения): opt-in через существующий механизм
   `cfg(kani_smallsort_controls)` или отдельный cfg (`kani_smallsort_extended`) — выбрать и обосновать; ни одна
   гармоника не удаляется, тела/домены/assertions не меняются, только `cfg` на уровне item (и выбранные разбиения
   C3c). Проверить статически: каждое имя из scope.tsv присутствует ровно один раз и в нужной конфигурации
   (скрипт на Python, вывод в отчёт). Rustfmt:
   `/tmp/claude-0/-root/5ce1713f-0d75-4ce2-92ab-bcf1e5df1b74/scratchpad/rustfmt.sh --check --edition 2024 --config-path /tmp/claude-0/-root/5ce1713f-0d75-4ce2-92ab-bcf1e5df1b74/scratchpad/fmtcfg/rustfmt.toml <изменённые .rs>`
   — exit 0; строки ≤ 100.
