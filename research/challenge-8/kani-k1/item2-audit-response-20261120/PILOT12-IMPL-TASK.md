## Решение по Replace

Macros и transform на `0aac16ef62` создают весь return Replace через `any_modifies` → `kani::any<T: Arbitrary>`. У `(*const T, *const T, *mut T)` все элементы должны реализовать `Arbitrary`. Stock реализации для raw pointers отсутствуют. `any_ptr(storage)` — отдельный autoharness model, который не создаёт return, привязанный к аргументам этого вызова. Поэтому в подготовленном roster B18/B19 выполнить Check реального merge с **пустыми** verified и ordinary stubs, actual шагами, loop, odd copy и panic guard. Результаты Check шагов из A использовать для сверки контрактных ролей и границ, а не как активные Replace. В handoff записать отклонение от плана B и основание по пину. Патч tool, смена сигнатур, генерация arbitrary адресов и обычный stub вместо шага выходят за границы задания. Совместимость Replace шагов остаётся отдельной задачей после появления поддержки такого return. Сам `bidirectional_merge` возвращает `()`, поэтому это ограничение не блокирует контроль его caller Pre или последующий Replace целого merge после допуска его Check. - **Fixture.** В каждом `proof_for_contract(bidirectional_merge)` взять произвольный инициализированный `[u8;34]` и независимый `q:any<u8>` в `KeyLess<u8>`. Срезы делятся после девятого элемента. В proof domain numeric-order pre задаётся контрактом. Для основных корней не фиксировать байты, q или результат сравнения.
- **Pre.** Точная длина 18 или 19, читаемый и инициализированный source, writable dst на все N байтов и непересекающиеся области. Для обоих source halves числовой неубывающий порядок. Числовой pre должен иметь отдельную именованную роль `merge_halves_numeric_order` в `requires`, отделённую от геометрии. Сделать предикат total на неподходящих длинах, capture для inactive T/F без чтений. `old` читает только доступный source и захватывает q, длину и пороговый target. Пороговая монотонность при одном q недостаточна для numeric Pre.
- **Actual loop и footprint.** Сохранить единственный `modifies` на dst[0..N]. Девять up пишут offsets 0..8. Девять down пишут offsets 9..17 для N18 и 10..18 для N19. У N19 actual odd copy записывает offset 9. В handoff привязать полное покрытие к actual copy на каждом шаге, адресному движению и отсутствию отказа до возврата. Сохранить обычные safety/unwind проверки и достижимый возврат. Финальный guard сравнивает `left/left_end` и `right/right_end`. Его actual panic path остаётся видимым. Чтение результата только после записи всего активного диапазона. Не читать old dst и хвост scratch, не материализовать `[u8;32]` через `assume_init`. Результат OFF относится к точной scratch-геометрии. Native uninit/validity требуют отдельной проверки.
- **Post.** Маска результата `>= q` по всем N элементам dst равна order-stat target исходного source при том же q. Проверить неизменность q и всего V34 source; внешний destination footprint проверяется DFCC без чтения неинициализированных байтов. Проверить normal return, bounds, unwind и `assigns`. Covers по q endpoints, split, ties, absence q и возврату. Делать covers на точных входах, которые удовлетворяют numeric Pre. N19 отдельно зафиксировать достижимость literal odd маршрута по исходнику и useful return. В stage B ещё нет `small_sort_network` caller, поэтому Pre и copy-back этой сети остаются пакету C. ## Два контроля

1. **Numeric Pre N18.** Plain proof с ровно `stub_verified(bidirectional_merge)` и без ordinary stubs. Литеральная геометрия как у B18, валидный writable scratch и активный `u8/KeyLess<u8>`. Активный source `[1, 0 × 16, 1]`, q=2. До вызова покрыть этот вход, обе q-монотонные половины и числовую инверсию слева. Передать вход в Replace, чтобы проверился **caller** `requires`. Ожидать одну `FAILURE` по `merge_halves_numeric_order`, сохранённые geometry/activation checks, достижимые pre-call covers. Отказ не должен зависеть от panic actual merge или от вычисления post уже после вызова. Контроль измеряет проверку Pre. Native outcome провайдера B остаётся самостоятельным.
2. **H10 literal witness.** Новый selector в прежнем `merge_a`, с теми же verified stubs `{swap_if_less, insert_tail}` и тем же `sort_right_ten` на `v[10..20]`. Активные 10 входных байтов задать нулями **до** вызова, q=2, остальной V34 произволен. После actual маршрута без символьной развилки записать `v[10]=1, v[11]=0`. Сохранить q-post на старом span, q-frame и V34 frame. Проверить числовой порядок той же функцией модели с единственной ожидаемой `FAILURE` `MB_H10_LITERAL_CORRUPT_NUMERIC_ORDER`. Оставить короткий cover достигнутого свидетеля/порчи до назначенного assertion и унаследованный cover numeric prefix внутри `sort_right_ten`. Общий набор mixed/ties/q endpoints здесь не нужен. Так проверяется тот же путь обнаружения инверсии при неизменных q-битах на фиксированном свидетеле. Positive H10 и прежний универсальный контроль сохраняются. Фиксированный q относится только к контролю. [Точный H10 маршрут и исходный контроль](/root/verify-rust-std-ch8-q-pilot-v1/library/core/src/slice/sort/shared/smallsort/verify/sorting_q_merge.rs:382)

## Оценка памяти для полных N18/N19 и варианты пакета C

В A обе H9-зависимости дали по 5,66 GiB sampled PGID, H10 — **9,94 GiB** (10 420 044 KiB), запас к 10 GiB около 64 MiB. У H10 доминирует driver bucket, backend достиг отдельно около 2,17 GiB. У старого H10-control driver также достиг cap, child 277,608 с, результат `INCOMPLETE`. Эти пики разделены по scope и времени. Для N18 есть запас 4,34 GiB относительно одиночной H9, но в полном графе две сети и новый merge. N19 добавляет левую H9 к правой H10 с почти исчерпанным запасом. **N18 имеет высокий риск превышения 10 GiB, N19 следует планировать как вероятный cap hit без разбиения.** Сумма пиков отдельных harnesses не прогнозирует RSS единого root. B отдельно даст стоимость actual merge и его coverage. [Данные пакета A](run-44872078840/raw/ch8-q-pilot-44872078840-1/q-pilot-raw.json)

Следующие решения относятся к C и выбираются после замеров B.

1. **Развязать две половины на существующей границе `sort9_optimal`.** Предпочтительный proof path при cap. Проверить отдельный Kani-only PFC этой функции на трёх точных geometry из A (base1/len9, base10/len9, base10/len10). Сводка включает числовой порядок и q/order-stat первых 9, q-frame, неизменный хвост при len10, footprint первых 9. По эффекту можно отдельно измерить один fixed-size диапазон записи для байтового Replace, чтобы не делать серию slice havoc записей. В полном consumer Replace двух actual вызовов sort9 передаёт проверенные факты одному состоянию; затем единственный правый insert даёт numeric order 10-байтного span, проверяется numeric Pre merge, а после него выполняется actual copy обратно. A-пробы сами по себе не регистрируют contract summary, поэтому C нельзя закрывать простой подстановкой `assume(sorted)` из раздельных корней. Стоимость DFCC у нового PFC sort9 открыта. Сначала точный пилот одного провайдера.
2. **Уменьшить backing только в сравнительном измерении.** Для N18 хватит V20, для N19 V21 с прежним base1 и canary с каждой стороны. Scratch остаётся 32, как в runtime. Это приближает модель к минимальной геометрии и может упростить frame, но влияние на driver RSS неизвестно. Старые провайдеры измерены на V34. Для меньшего backing требуются совпадающие физические domains или доказанный перенос границ/pre/footprint. Успех V20/V21 не засчитывается за V34. На квалификационном V34 прежде стоит испытать компактный эквивалентный итоговый byte-frame и разделение независимых proofs/covers по exact roots, сохранив те же pin, fixture, режимы и все необходимые роли.
3. **Если actual Check merge сам упирается в ресурсы**, сохранить точное unresolved состояние B. Проверить раздельно курсорное/footprint обязательство и q-пост на той же source geometry как измерения. Полная сводка требует связанного доказательства обоих и applicability. Для ускорения через step Replace нужен отдельно доказанный способ возвращать те же pointers с надлежащим provenance. До этого честный потребитель исполняет actual merge либо использует успешно проверенный **целый** merge с return `()`. Пределы памяти, runtime и обязательные safety checks при выборе кодировки сохраняются.
