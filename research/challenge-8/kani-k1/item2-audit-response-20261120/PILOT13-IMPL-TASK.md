## Проверки и привязка сводок

1. **До merge.** Сверить все 50 фактических swap с MA-SWAP-BYTE-Q. Провайдер покрывает V34, base 1 или 10, `a < b < 9`, все байты и q. Одновременно действуют q AND/OR, полный byte min/max и footprint двух байтов. У правого insert доказать native caller Pre, включая q-монотонность старого префикса. Условный numeric post вставки переносит числовой порядок с первых девяти байтов на все десять. На actual вызове whole-merge Replace отдельно сверить native caller Pre `merge_halves_numeric_order` для обеих половин и `merge_geometry`. Не добавлять assumptions об отсортированности половин. Успех A-проб половин служит для сверки маршрута и стоимости.
2. **Merge и copy-back.** Replace целого `bidirectional_merge` с return `()` использует точный Check B18/B19. Область записи — первые N байтов отдельного actual `MaybeUninit<[u8;32]>`, destination offset 0, source — исходный активный срез после presort. Сверить initialized readable source, writable disjoint destination, сохранение source/q и запись всех N слотов в actual провайдере. У N19 запись среднего слота относится к actual odd copy в Check B19. В consumer `merge_up/down` и odd copy покрыты этим провайдером, а `copy_nonoverlapping` из scratch обратно в активный срез исполняется телом network. Сохранить writable-only pre, без old-read destination и без чтения или материализации хвоста scratch. OFF оставляет обычные memory, bounds, overflow и unwind checks. Native uninit/validity требуют отдельной ON-проверки. [Геометрия и q-post сводки B](/root/verify-rust-std-ch8-q-pilot-v1/library/core/src/slice/sort/shared/smallsort/verify/sorting_q_merge_model.rs:299) · [Обязательства провайдера B](PILOT12-IMPL-TASK.md)

Проверить `merge_b::merge_q_post` по тому же диапазону в исходном backing после copy-back и тому же q. Использовать готовый oracle B до N19, сохранив прежний CAP=17. ## Память и следующий шаг при cutoff

В A одна H9 потребовала 5,66 GiB, а H10 — 9,94 GiB, то есть около 64 MiB запаса до nominal cap. Облегчённый H10-control в 12b занял 8,22 GiB. Полный no-merge N17 в кампании 9 занял 9,04 GiB. Отдельные actual Check merge N18/N19 в 12b заняли 4,49/4,70 GiB при 193/197,8 с VT. Стоимость whole-merge Replace внутри сети отличается от standalone Check. В C остаются обе сети с байтовыми сводками, numeric Pre, havoc scratch, actual copy-back и итоговые проверки. **N18 проверяем с высоким риском cutoff, N19 планируем как ещё более рискованный** из-за правой H10. Пики разных корней не складывать. Для N19-control экономия от литерального входа правдоподобна, fit всё равно предстоит измерить.
