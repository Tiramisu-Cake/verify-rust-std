# Модель стоимости оракулов SmallSort на уровне SAT

Приложение к [`../AUDIT-REPORT-CH8-ITEM2-STATUS-RU.md`](../AUDIT-REPORT-CH8-ITEM2-STATUS-RU.md) (аудит от 2026-11-20).
Это не Kani и не доказательство: это быстрый способ сравнить формулировки постусловий
до того, как тратить на них запуск CI.

## Что моделируется

Элемент — 8-битный ключ, сравнение `<`. Перемещения элементов заданы мультиплексорами,
указателей и модели памяти нет. Сети `sort9_optimal` и `sort13_optimal` извлечены из
`smallsort.rs` на `7b31b060` скриптом `extract_nets.py` (25 и 45 компараторов; обе
сортируют все 0-1 входы). Вставка и `bidirectional_merge` записаны по тексту того же
файла. В CNF утверждается отрицание свойства: `UNSATISFIABLE` значит «свойство верно
на всех входах».

| Скрипт | Что строит |
|---|---|
| `gen.py <модель> <оракул> out.cnf` | `net9`, `net13`, `net17`, `insK`; оракулы `sorted`, `countN2`, `harness`, `count_q`, `harness_q`, `ge_q`, `qform`, `qform_lemma`, `count_q_lemma`, `tag_onehot` |
| `gen2.py <имя> <N> out.cnf` | пороговые контракты вставки (`ins_qform_lemma`, `net17_qform_lemma`), лист `insert_tail` (`ins_leaf_qform`, `ins_leaf_std`), целые маршруты из одних сводок (`general_ind_*`, `network_ind_*`) |
| `gen3.py <имя> <N> out.cnf` | лист `bidirectional_merge`: `merge_std`, `merge_A*`, `merge_B`; `ins_leaf_A` |
| `gen4.py <имя> <N> out.cnf` | потребитель, который видит только сводки вызываемых: `ins_stub_count`, `ins_stub_thr` |
| `gen5.py <N> plain\|step\|inv out.cnf` | merge в пороговой форме: без лемм, с фактами шага, с фактами шага и инвариантом курсоров |

Соответствие оракулов: `countN2` — нынешний `sorting_model::post` (счёт по каждому
входному значению); `count_q` — гипотеза из §6.1 отчёта (один произвольный `q`);
`qform` — порог `x >= q`: монотонность индикаторов и равенство их числа;
суффикс `_lemma` — те же цели плюс факты, которые потребитель получил бы из
контрактов вызываемых функций.

## Как запустить

```sh
cc -O2 -o cdcl cdcl.c                 # маленький CDCL, написан для этого аудита
python3 gen.py selftest               # схемы совпадают с sorted() на случайных входах
python3 gen3.py selftest
python3 check_solver.py               # решатель против полного перебора и на сломанных сетях
python3 check_lemmas.py               # все внедрённые леммы истинны на случайных допустимых входах
./run.sh gen.py 60 net13:harness net13:harness_q net13:qform_lemma
./run.sh gen2.py 60 net17_qform_lemma:17 general_ind_ostat:32
SOLVER=kissat ./run.sh gen.py 600 net13:harness net13:qform_lemma   # то же на настоящем решателе
```

`results-raw.txt` — мои прогоны на двух ядрах. `UNKNOWN` значит, что исчерпан лимит
процессорного времени; он виден в поле `time`.

## Границы

- Решатель `cdcl.c` — минимальный CDCL без препроцессинга. Абсолютные времена с Kani
  (CaDiCaL внутри CBMC) не сопоставимы; значим порядок величин и то, какие формулировки
  решаются за сотни конфликтов, а какие не решаются за миллионы.
- Формулы на 1–2 порядка меньше настоящих (у вас 455 тыс. переменных на N13, здесь тысячи).
- Леммы проверены тестами и тем, что цель с ними выводится; их доказательство на настоящих
  телах функций — отдельные обязательства в Kani.
