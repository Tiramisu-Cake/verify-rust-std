## Привязки к source и lowering

В таблицах ниже `#` обозначает напечатанный ordinal конкретного root. Для компактных списков `root + #` однозначно восстанавливает полный ID, статус и location в JSONL. `S` — `library/core/src/slice/sort/shared/smallsort.rs`, `H` — `smallsort/verify/sorting_q_merge.rs`, `Q` — `smallsort/verify/sorting_q_model.rs`, `M` — `smallsort/verify/sorting_q_merge_model.rs`, `P` — `smallsort/verify/sorting_q_pilot.rs`. Последние четыре пути заданы относительно `library/core/src/slice/sort/shared/`. Все source anchors читаются из std commit соответствующего root. Regular Location сохраняет spans, которые Kani печатает для generated closures и macro expansions. Например `NM-S13-L13` печатает `S:609:1` для ensures, активное условие находится в `S:626` и связывается с ним по целевому Check, сгенерированной closure и выражению целиком.

Kani выбирает SimpleCheck для proof target и Replace для verified stub. В Check requires становятся assumptions, `old` снимается после них, actual тело исполняется с DFCC-параметрами `modifies`, ensures проверяется assertion. В Replace requires становятся assertions, `old` снимается после них, `write_any` меняет только объявленный footprint, ensures становится assumption после havoc. В карте ниже singleton-site связь опирается на exact harness, выбор режима, активное выражение и единственный достижимый source call. Для `old`/havoc/assume на таком вызове это source/transform связь. Свойства безопасности в общих helper/DFCC routines сгруппированы по native ID и source роли. Их разбиение по каждому вызову требует lowering с call-site provenance. [Kani mode selection](/root/kani-upstream-ch8-s1/kani-compiler/src/kani_middle/transform/contracts.rs:569) · [Check](/root/kani-upstream-ch8-s1/library/kani_macros/src/sysroot/contracts/check.rs:23) · [Replace](/root/kani-upstream-ch8-s1/library/kani_macros/src/sysroot/contracts/replace.rs:101)

CBMC 6.11.0 присоединяет к цели все включённые SSA asserts с тем же property ID и проверяет их конъюнкцию. Regular stdout даёт результат цели, состав SSA instances и guards в артефактах отсутствуют. Для общих sort9/insert IDs установлена роль на уровне декларации. Для каждого повторного исполнения остаётся подтвердить присутствие соответствующего assertion в группе, его guard и привязку `old`, footprint и post assumption к тому же состоянию. Для generic copy/assigns остаётся связать origin каждого relevant write с нормализованной целью. ## Mixed-OB review и следующий минимум

OB11 и OB12 делят 64-битный указатель на 11+53 и 12+52 бит соответственно. Для bridge нужна инъективная перестановка используемых object IDs с сохранением reserved IDs, same-object/provenance и границ. Наши source offsets помещаются в оба signed offset поля. Presort оперирует байтами V34 и compare без порядка между разными allocations. Insert сравнивает указатели в V34. Тот же ID сокращается в checked subtraction одинакового base, для u8 byte count равен rel+1. Для merge source V34 и scratch32 раздельны, сравнения cursor идут внутри source, reverse sentinel `src-1` — offset 0 в V34. В начале шага i ни один поток не выбрал больше i байтов из половины длиной ≥floor(N/2), поэтому sentinel нужен для сравнения границ и не читается. Scratch offsets лежат в `[0..N)` до copy-back, q unchanged. Для 11→15 сохраняется active A insert, для 12b→15 active B merge, для 16→17A active wide clauses и тела, для 17A→17B same std pin. Это source-инварианты. Receipt подтверждает capacity для каждого из фактически завершившихся roots. У целевой invocation нет связанного GOTO/SSA свидетельства о полном ребре и соответствии pointer encoding. [Исходная матрица и диапазоны](QUALIFICATION-AND-ADMISSION-N13-N20.md#4-mixed-object-bits)
