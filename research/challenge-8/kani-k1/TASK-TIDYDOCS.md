## Правила для комментариев (согласованы с владельцем)

1. Никакой истории разработки: убрать `GCB`, `G1`/`G2`, `lane`, `REALCONTRACTSTWO`, «prior … SUCCESS», «original»,
   «historical», «Part 1/Part 2», «research roots», ссылки на этапы и порядок появления кода.
2. Не пересказывать атрибуты и код (`T = u8; F = …; unwind 50; default solver` над функцией, где это видно).
   Писать только **почему**: почему такой `unwind`, такой солвер, такой набор длин, такая заглушка, такой оракул.
3. Перечень доменов и общую оговорку о scope держать **в одном месте** — короткая карта в `verify.rs`. В остальных
   файлах — только то, что нужно для понимания конкретного кода рядом.
4. SAFETY-комментарии и настоящие обоснования (почему заглушка корректна, почему оракул независим от ключа, почему
   пара leaf/consumer согласована) **сохранить**; сокращать можно, удалять нельзя.
5. Короткие нормальные английские предложения, стиль комментариев std. Без цепочек через слэш (`T/F/backing`,
   `u8 backing9/13`), без канцелярита и без повторных оговорок в каждом абзаце.
6. Не добавлять новых утверждений о результатах и не ослаблять существующие оговорки. Причины, которые не
   установлены, не формулировать как установленные.
7. Целевого процента сокращения нет; критерий — ясность.

## Frame на настоящих хелперах

Контракты пяти хелперов (`swap_if_less`, `insert_tail`, `insertion_sort_shift_left`, `sort4_stable`,
`bidirectional_merge`) перечисляют в `modifies` только память элементов/приёмника. Компаратор `is_less` может писать
и в другую память (захваченный счётчик, static, память по ссылкам из элементов); Kani не умеет выразить footprint
произвольного `FnMut`. Поэтому:

- Над контрактом `swap_if_less` в `smallsort.rs` — комментарий 3–5 строк: write sets перечисляют только
  element/destination memory; контракты заявлены и могут использоваться через `stub_verified` только для
  компараторов, которые ничего не пишут вне перечисленных мест, **и только на доказанных доменах (тип, компаратор,
  аллокация), перечисленных в `verify.rs`**; один успешный PFC не обосновывает новый consumer. У остальных четырёх —
  короткая отсылка к этому комментарию.
- В карте `verify.rs` — то же одним абзацем, плюс ссылка на новый контроль.

## Контроль

Новый opt-in (`#[cfg(kani_smallsort_controls)]`) отрицательный контроль в `realcontracts.rs`, например
`rejects_swap_comparator_writing_outside_frame_u8`: `#[kani::proof_for_contract(swap_if_less)]` на `[u8; 4]`,
законный порядок `*a < *b` с захваченным счётчиком, который обновляется через `wrapping_add` (чтобы исключить отказ
по переполнению), вызов настоящего `swap_if_less` на позициях внутри массива.

**Ожидание:** результат FAILED, и **все** упавшие проверки — проверки write set (assigns/modifies) на записи
счётчика. Любой другой упавший check (переполнение, dereference, requires) — контроль не откалиброван: записать и не
выдавать за успех. Точный текст проверки зафиксировать по первому запуску.
