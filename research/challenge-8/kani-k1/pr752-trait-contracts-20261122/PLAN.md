## GO на один dispatch fork CI

- Пин и база сверены, кандидат чистый и заморожен по SHA/tree. Есть review semantic diff, карта шести реализаций и точного scope каждого Check/Replace, `FMT_OK` и ожидаемая дельта имён `235 + 10`. Pin-файл, `kani.yml`, скрипт и flags организаторов остаются теми же. Opt-in controls исключены из обычного набора.
- Кандидат и предложение GO содержат fork ref, expected head SHA/tree, workflow `kani.yml`, baseline run и таблицу времени по harness. `scripts/run-kani.sh` берёт **полный** std inventory, объединяет standard/contract entries и режет его на четыре последовательных куска по `ceil(count/4)`. Новые записи могут сдвинуть границы. Использовать доступный точный inventory для оценки размещения, а при его отсутствии явно пометить оценку предварительной. 235/245 относятся только к SmallSort.
- Семь перенесённых roots стоили 596,7 с суммарного native VT в G3. Три default Check добавляют ориентировочно 60–240 с. **Оценка нового serial VT — около 11–14 мин**, по текущим данным это объём работы, а wall time зависит от шардирования и конкуренции. Рабочий ориентир для согласования — не больше **+5 мин к 77 мин** для самого длинного verifier shard. По возможности смотреть длительность verify step отдельно от setup и очередь отдельно от исполнения.
- Координатор фиксирует отдельный GO для этого SHA, временно включает workflow в форке и делает один `workflow_dispatch` на выделенном ref. После приёма dispatch вернуть прежнее состояние workflow по той же процедуре, что в baseline. Решение по GCB и отдельному controls-on прогону принадлежит координатору. Задание воркеру заканчивается подготовкой локального кандидата.
