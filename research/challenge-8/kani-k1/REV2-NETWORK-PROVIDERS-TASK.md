# REV2 · задание на удешевление sort13 и merge

**Перенос всей сети N13–N32 в pr752 на ближайшие одну-две недели не планировать.** Для текущих Check нужен выигрыш по VT примерно в **7,3×** у sort13 и **5,9×** у merge N32 и снижение пика группы примерно на **55–56%**. Успешные Linux-проверки с прежней кодировкой далеки от обеих границ. На macOS S13 и Mask ещё не измерены, а Below дошёл до временной отсечки. Оценка на первый тест достижимости — **1–2 инженерных дня и один Ubuntu run**. Только при успешных граничных корнях стоит оценивать перенос, ориентировочно ещё **1–2 инженерные недели и 4–6 запусков** на macOS, exact геометрии, потребителей и штатные партиции. Если потребуется новый способ связывать индукцию с исполняемым кодом, эта оценка неприменима. [Решение владельца](OWNER-DECISION-LIMITS-20261125.md) · [CAL2 Ubuntu](CAL2-RESULTS-ANALYSIS.md#сравнения-ubuntu) · [CAL2 macOS](CAL2-MAC-RESULTS-ANALYSIS.md#macos-и-ubuntu)

Подготовь пакет параллельно переносу fallback N7. Цель — понять, насколько помогает вынести динамический write set из длинного тела и сколько стоит одна проверяемая ступень каждого алгоритма. Подготовка и handoff локально, запуск после независимого ревью и отдельного GO. Runtime std, штатный workflow и опубликованные домены pr752 сохраняются.

## Sort13 · один Check листа и реальная сеть со сводкой

1. Под opt-in cfg добавь к существующему `swap_if_less` функциональный Check только для `u8/KeyLess<u8>` в V34/base1. `KeyLess<u8>` сравнивает полные байты по `<`, а независимый q служит наблюдателю. Используй два уже существующих тонких targets в `modifies` и действующие safety preconditions. Новый post — точные `(min(old_a, old_b), max(old_a, old_b))` по полным байтам, неизменный q. `old` читает только два разрешённых initialized адреса. В `S13-SWAP-LEAF` взять любые `0 ≤ a < b < 13`, таким образом охвачены все 45 ordered пар. Проверить byte frame всех других позиций V34, штатную безопасность и unwind. Covers на swap/no-swap, равные байты в разных ячейках, mixed q и normal return. Напечатать статическую сверку 45 пар с доменом листа. Без stubs в листе. [Реальный swap и две записи](/root/verify-rust-std-cal1-w11/library/core/src/slice/sort/shared/smallsort.rs:441) · [Прецедент байтового листа](item2-audit-response-20261120/PILOT11-IMPL-TASK.md#check-swap-и-правой-вставки)
2. `S13-PLAIN-BYTE` — обычный `Proof` на тех же произвольных V34, `v[1..14]`, `u8/KeyLess<u8>`, независимом q, unwind 36. Исполняется реальный `sort13_optimal` и его 45 call sites, только `swap_if_less` заменён `stub_verified` листом из п. 1. В harness явно проверь те же presort geometry, числовой порядок префикса, равенство числа `<q` на полном диапазоне q, q-frame и byte frame остальных ячеек. Сохрани смысл CAL2 covers. Достижение реального comparator cover подтверждается в листе, где comparator исполняется. Проверь свойства входа листа на всех вызовах и что реальное тело sort13 вне этих вызовов не пишет данные backing. [Реальный S13](/root/verify-rust-std-cal1-w11/library/core/src/slice/sort/shared/smallsort.rs:577) · [Предикаты presort](/root/verify-rust-std-cal1-w11/library/core/src/slice/sort/shared/smallsort/verify/cal1_q_merge_model.rs:57)

Это тест прямого маршрута с вынесенными pointer/copy/lifetime проверками, которые выполняются в отдельном листе. Обычный `Proof` проверяет явные свойства harness, а проверка каждой записи остаётся в Check листа. `S13-PLAIN-BYTE` не регистрирует Check провайдера `sort13_optimal` для имеющихся `stub_verified(sort13_optimal)`. Для следующих потребителей либо исполняется это же реальное тело с проверенным листом, либо отдельно доказывается новая механическая граница. Старую сводку sort13 этим результатом не заменять. Если полные min/max всё ещё дороги, следующий архитектурный вариант — конечная 13-битная схема по тем же 45 парам и checked переход пороговых AND/OR для каждого actual swap. Кандидат требует привязки порядка пар, байтового frame и отдельного числового порядка из результата для всех q. Проверка одной скопированной таблицы в harness такой привязки не даёт. [Границы plain-композиции](item2-audit-response-20261120/PILOT7-PLANNER-NOTE.md)

## Merge N32 · цена actual тела и шаг для индукции

1. `M32-PLAIN-MASK` — обычный `Proof` с полным actual `bidirectional_merge`, без stubs и верхнего Check. Сохрани CAL2 Mask, числовой неубывающий порядок обеих произвольных initialized половин `[1..17]` и `[17..33]` в V34, независимый q и отдельный `MaybeUninit<[u8;32]>` scratch от offset 0. Явно проверь применимость read/write/disjoint и числового Pre. Его можно задать как предпосылку fixture на входе провайдера, которую позже надо доказать у caller. Проверяй результат той же q-маской, q/source V34 frame, actual cursor guard, штатные memory/bounds/unwind и полезный возврат. Сохрани CAL2 covers, включая cross-half ties и чередование половин. Сохрани привязку чтения результата к 16 up/down парам, каждая пишет свои два слота. Не читать old dst. Проверка N32 ограничена чётной длиной. [Fixture CAL2](/root/verify-rust-std-cal1-w11/library/core/src/slice/sort/shared/smallsort/verify/cal1.rs:94) · [Тело merge](/root/verify-rust-std-cal1-w11/library/core/src/slice/sort/shared/smallsort.rs:945)
2. `M32-PAIR-STEP` — диагностическая лемма на одной паре **actual** `merge_up` и `merge_down`. В том же V34 и scratch выбери произвольный номер `0 ≤ k < 16` и независимые front/back offsets. Сумма потреблённых слева и справа равна k отдельно для каждого направления. Выводи in-bounds чтения из этих целочисленных границ. Суммарно между направлениями половина уже может быть исчерпана, поэтому не добавляй предпосылку о непустом остатке каждой половины. Проверяемый результат шага — выбранный полный байт с точным tie правилом, запись только в `scratch[k]` и `scratch[31-k]`, точные обновления курсоров, q/source frame и штатная safety. Для нативного write set используй verification-only Check с возвратом `()` и двумя точными targets. Тройки указателей, полученные от actual шагов, проверяются в этом корне, а допустимые граничные `wrapping_sub` указатели не разыменовываются. Сохрани covers выбора каждой стороны, tie и k=0/15. Лемма измеряет стоимость локального шага. [Actual up/down](/root/verify-rust-std-cal1-w11/library/core/src/slice/sort/shared/smallsort.rs:841)

Если полный plain merge дорог, путь к удешевлению — индукция на **двух направленных проходах**, а не ещё один вариант Mask. Каждое направление эквивалентно выбору очередного экстремума в своём представлении исходных половин. Фиксированный полный порядок по `(байт, левая/правая половина, индекс)` делает ties согласованными, up берёт левый, down правый. Инвариант связывает четыре счётчика потребления, два заполненных диапазона scratch и q-границу на выходе. Нужны база, сохранение инварианта, disjoint выбранных позиций в общем порядке, точная финальная проверка курсоров и заполнение всех N, включая separate odd copy для нечётных длин. Никаких предположений, которые запрещают чтения уже выбранных ячеек, если actual код их читает. Лемму надо механически связать с реальным циклом, например через проверяемую Kani-only аннотацию инварианта на существующей границе `for`, если её поддержка и стоимость подтверждены. В эту задачу такую переделку не включать. Stock Replace для `merge_up/down` с кортежами raw pointers не использовать. На пине генератор результата требует `Arbitrary`, а отдельный wrapper из fixture не является точкой вызова в runtime merge. Успех plain N32 или шага не даёт права `stub_verified(bidirectional_merge)`. [Предыдущее ограничение Replace](item2-audit-response-20261120/PILOT12-IMPL-TASK.md#решение-по-replace) · [Прежняя exact квалификация N32](item2-audit-response-20261120/ADMISSION-N32.md)

## Решение после первого пакета

- При завершившихся S13-PLAIN-BYTE и M32-PLAIN-MASK в лимитах вместе с нужным листом стоит сделать один matched macOS run этих путей и измерить N13/N32 с actual consumer. Затем проверять N17, N18/19, правый sort13 и нечётный merge. Для macOS сохранить 4 GiB на новый корень, reserve 1,25 GiB и live pressure. Штатные сочетания jobs, 10/5 GiB группы и +5 мин на критическую партицию проверяются отдельно. Успех Linux, лемм и старых consumers этих критериев не закрывает. [Геометрии N20–N32](item2-audit-response-20261120/MERGE-WIDE-PLAN.md) · [После CAL2 macOS](CAL2-MAC-RESULTS-ANALYSIS.md#рабочие-ориентиры-и-решение-по-batch)
- Если проходят только лист и пара шагов, записать «текущий прямой путь не достигает лимита» и оценить архитектурный перенос по указанным границам. При 130–200 с решение об исключении остаётся у владельца. Текущая приёмка его не допускает. При отсечке не поднимать cap и не расширять roster на N13–N32. Пины и ширину согласовывать до какого-либо нового `Check → Replace` ребра. Доказательство на `u8` не закрывает `u64`.
