### Текущее поведение

`-Z valid-value-checks` включает `ValidValuePass` на мономорфизированном MIR после преобразований контрактов. Проход находит операции с риском создания или использования невалидного типизированного значения: отдельные raw deref, union-reads, преобразования представления, mutable casts и некоторые присваивания. По layout он извлекает условия вида «смещение, ширина, допустимый диапазон», например 0/1 для `bool` и два диапазона для `char`. Сгенерированный MIR проверяет биты целочисленным чтением до опасной операции и добавляет safety assert/assume либо failing unsupported guard. Проход полагается на типовую валидность многих обычных MIR-операндов. Отдельный, более поздний `UninitPass` отслеживает инициализацию байтов, включая перенос её состояния при copy и установку при `write_bytes`. Инициализированный байт может нарушать ограничения типа, поэтому эта информация сама по себе не решает 3762. | `copy` | Перекрывающаяся операция приходит как вызов. В `visit_terminator` для неё нет отдельной проверки или учёта изменения памяти. Бэкенд выполняет перенос через `memmove`, для nonoverlap — через `memcpy`. При смене типа указателя путь может отдельно остановиться на консервативной проверке mutable cast. Так запись через `*mut u32` в хранилище `char` может быть отвергнута ещё до `copy`. Прохождение самого вызова тоже не доказывает, что последующее обычное чтение `char` проверено. [Обработка вызовов](https://github.com/model-checking/kani/blob/bcdc1a0f8dc566654da1f18b4e502f0f4e7ad40a/kani-compiler/src/kani_middle/transform/check_values.rs#L537-L590) · [Mutable cast](https://github.com/model-checking/kani/blob/bcdc1a0f8dc566654da1f18b4e502f0f4e7ad40a/kani-compiler/src/kani_middle/transform/check_values.rs#L696-L753) · [Бэкенд copy](https://github.com/model-checking/kani/blob/bcdc1a0f8dc566654da1f18b4e502f0f4e7ad40a/kani-compiler/src/codegen_cprover_gotoc/codegen/intrinsic.rs#L1115-L1187) |
| `write_bytes` | Для известного layout со строгими диапазонами проход проверяет, что `size_of::<T>()` повторов байта уже образуют валидное `T`. Эта проверка не учитывает `count`, а для неподдерживаемого layout есть отдельный unsupported guard. При `count == 0` память не меняется. При ненулевой записи допустимо оставить невалидные для `T` биты в сырой памяти, пока из них не получено значение `T`. Issue 5190 приводит оба ложных отказа для `MaybeUninit<char>`. ### Что исправлять

- Сохранить побайтовую семантику операций и самостоятельные проверки размера, выравнивания, допустимого доступа и непересечения для nonoverlap. `copy` должен сохранять результат, эквивалентный чтению источника до записи при перекрытии. Ни copy, ни memset сами по себе не создают значение `T`. Объект с записанным суррогатом может быть перезаписан валидным `char` до типизированного чтения. Именно различие между этим случаем и фактическим чтением суррогата демонстрирует 3762. [Kani 3762](https://github.com/model-checking/kani/issues/3762) · [Семантика ptr::copy](https://doc.rust-lang.org/core/ptr/fn.copy.html) · [Семантика ptr::write_bytes](https://doc.rust-lang.org/core/ptr/fn.write_bytes.html)
- Проверять представление при типизированном использовании затронутой памяти, включая доступ через алиас и обычное чтение локальной переменной после записи через её адрес. Для ограниченного домена можно отслеживать потенциально изменённые диапазоны и применять layout-проверку того типа, которым их затем читают. Проверка должна смотреть на сырые биты до типизированной загрузки, способной потерять исходное представление. Для широкого домена нужны корректные правила для вызовов, частичных перезаписей, union/enum и ниш, `MaybeUninit` и padding, а также взаимодействие с моделью инициализации и provenance. Один `*mut u8` недостаточен для вывода об отсутствии обязательства: за ним может стоять `bool` или `char`. Простое удаление unsupported guard пропустит некоторые невалидные чтения. [Инструментирование deref](https://github.com/model-checking/kani/blob/bcdc1a0f8dc566654da1f18b4e502f0f4e7ad40a/kani-compiler/src/kani_middle/transform/check_values.rs#L608-L656) · [Layout-проверки](https://github.com/model-checking/kani/blob/bcdc1a0f8dc566654da1f18b4e502f0f4e7ad40a/kani-compiler/src/kani_middle/transform/check_values.rs#L1076-L1139)
- Регрессии должны отличать запись без чтения, чтение невалидного `char` или `bool` через исходный тип и перезапись до чтения. Нужны также нулевой и символический count, ZST, перекрытие, сохранение padding/init-state и обе проверки ON одновременно. Для неподдержанных алиасов и layout оставить явный отказ. Проверка только raw deref недостаточна для снятия общего запрета. [Существующие проверки niche и copy](https://github.com/model-checking/kani/blob/bcdc1a0f8dc566654da1f18b4e502f0f4e7ad40a/tests/expected/valid-value-checks/custom_niche.rs#L105-L127)

**Узкий первый PR реалистичен.** Для 5190 можно обусловить синтетическую проверку и её unsupported guard наличием записи, сохранив проверки указателя и оставив прежнее поведение для ненулевых записей. Оценка — десятки строк плюс регрессии, 1–3 инженерных дня. Это закрывает случай нулевого count. Первый содержательный PR для 3762 реалистичен для явно ограниченного, проверяемого класса переносов, если компилятор может доказать допустимый layout хранилища и последующих typed uses либо инструментировать их. Сначала стоит доказать это на локальной памяти и простых скалярных layout, с отказом вне домена. Для такого фрагмента ориентир — несколько инженерных дней и порядка сотен строк с тестами. Общая поддержка обеих copy-операций и ненулевого `write_bytes` — несколько сотен строк или больше и ориентир 2–4 недели на реализацию и регрессии. Риск высокий: неполный учёт алиасов даёт ложный SUCCESS, слишком широкая инвалидизация даёт ложные отказы или рост формулы. Если потребуется сопровождать по байтам состояние памяти через вызовы в backend, оценка увеличится. [Kani 3762](https://github.com/model-checking/kani/issues/3762) · [Kani 5190](https://github.com/model-checking/kani/issues/5190)

**Зависимость SmallSort.** `swap_if_less` выполняет `ptr::copy`, в том числе между совпадающими адресами, затем `copy_nonoverlapping`. Через него идут sort9 и sort13. `insert_tail` использует nonoverlap для сдвига и заполнения зазора через `CopyOnDrop`. Его вызывают fallback и досортировка половин. `sort4_stable`, а через него `sort8_stable`, копируют элементы в scratch. `merge_up`/`merge_down` и нечётный хвост `bidirectional_merge` пишут через nonoverlap. General использует его при заполнении scratch и в восстановлении `CopyOnDrop`, network — при обратном копировании после merge. В runtime `smallsort.rs` прямого `write_bytes` нет. Малый фикс 5190 сам эти пути не разблокирует. Для SmallSort практическая цель 3762 — принять реальные побайтовые переносы в инициализируемый scratch и обратно, сохранив проверки при последующем типизированном использовании. Это отдельное обязательство пункта 1, помимо функционального допуска пункта 2.
