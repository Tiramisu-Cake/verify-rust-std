## 3. Что изменить

### R1. Зафиксировать домен контракта сейчас: `len ≤ small_sort_threshold()`

План оставляет трактовку «сопоставить с challenge до заявления о полноте». Решать можно уже:

- Документация самих traits: порог — это длина, до которой вызов `small_sort` допустим (строки 21 и 70 исходника) [факт].
- Оба вызывающих quicksort проверяют `len <= T::small_sort_threshold()` перед вызовом
  (`stable/quicksort.rs:26`, `unstable/quicksort.rs:30`) [факт].
- Мейнтейнер-рецензент формулирует требуемое покрытие теми же порогами (таблица §1).

Правка: во все контракты трёх traits поставить единое `requires(v.len() <= Self::small_sort_threshold())`
(для Stable+Freeze дополнительно условие на scratch). Сейчас в G3 иначе: T1 допускает N>32 при большом scratch,
а T2/T3 допускают любую длину на fallback-маршруте (`threshold == FALLBACK || len <= threshold`) [факт].
Именно эти широкие `requires` и порождают в плане «обязательную ось» G4-L. Сужение до документированного
домена — не подгонка под зелёный proof; основание надо записать в комментарии к контракту.

Следствие: **пункт 2 становится конечной задачей** — 0..=16 для fallback-маршрутов и 0..=32 для general/network.
G4-L перестаёт быть условием полноты пункта 2. Из §4.2 уходит оценка «10–20+ дней» на функциональную индукцию.

### R2. Отделить произвольную длину `insertion_sort_shift_left` (пункт 1) от sorting

Неограниченная длина остаётся вопросом только для функции 5 из пункта 1. Достижимые вызовы в core дают
не больше 20 элементов (`select.rs` — 16, `stable/mod.rs` и `unstable/mod.rs` — 20, network — 17) [факт].
Два действия:

1. Спросить организаторов (вопрос уже задан на #56 и не отвечен).
2. Независимо от ответа сделать **safety-only** индукцию: инвариант из диапазонов указателей
   (`v_base+offset ≤ tail ≤ v_end`, `begin ≤ sift < tail`, `gap_guard.dst == sift+1`), без квантификаторов
   по содержимому. Для типов без невалидных битовых представлений (u8/u64) этого достаточно [гипотеза].
   Такой пилот не зависит от #5148 и на порядок дешевле функционального инварианта.

### R3. Ключ профиля — тип компаратора, а не адрес функции

Сейчас модель включается сравнением `*cmp as *const () == canonical_less_u64 as *const ()`, а `F` — это
`fn(&u64, &u64) -> bool` [факт]. Отсюда три проблемы:

- Вызов через указатель на функцию — ровно то, что uninit-анализ не поддерживает; план пункта 1 закладывает на A2
  10–20 дней и высокий риск ложного SUCCESS. Но `P::CMP` и `U64Cmp` — ваша верификационная обвязка: сам smallsort
  через указатели на функции ничего не вызывает. Зависимость создана профилем.
- Одна мономорфизация `F` на все компараторы сигнатуры: контракт вынужден инспектировать значение, появляется
  `enabled` как рантайм-условие.
- Равенство адресов функций в Rust не является семантическим тождеством. В модели Kani это не ломает корректность,
  но рецензент спросит.

Замена: ZST-компаратор с ручной реализацией `FnMut`, специализация `SortModel` по типу. Я проверил компиляцией
прототипа (rustc 1.97 с `RUSTC_BOOTSTRAP=1`, фичи `min_specialization`, `rustc_attrs`, `unboxed_closures`, `fn_traits`) [факт].
Первые три уже включены в `core/src/lib.rs` (строки 143, 152, 163); `fn_traits` объявлена в самом core:

```rust
#[rustc_specialization_trait]
pub(crate) trait OrdModel: Sized + Copy { type Key: Copy + Ord; fn key(&self) -> Self::Key; }
pub(crate) struct KeyLess;                       // один ZST на все моделируемые T
impl<'a, 'b, T: OrdModel> FnMut<(&'a T, &'b T)> for KeyLess { /* a.key() < b.key() */ }  // плюс FnOnce
impl<T, F> SortModel<T, F> for () { default fn modeled() -> bool { false } /* … */ }
impl<T: OrdModel> SortModel<T, KeyLess> for () { fn modeled() -> bool { true } /* … */ }
```

Замыкания и указатели на функции при этом попадают в ветку по умолчанию; вызов прямой (FnDef), A2 не нужен.
Ловушка: вариант `impl<T: OrdModel> SortModel<T, ModelLess<T>>` отвергается («specializing impl repeats parameter»).
Поддержку ручного `extern "rust-call"` в Kani я не проверял, но в #701 ровно такой приём используется на пине main;
один смоук-harness всё равно нужен.
A2 остаётся возможным upstream-вкладом в Kani, но уходит с критического пути.

### R5. Переформулировать §6.2: в Kani нет проверяемого ∀T-theorem

Kani проверяет только мономорфные экземпляры. «5–10 дней lifting, недели на checked generic theorem» —
это не срок, а смена инструмента. Честная структура:

1. Полная таблица классов маршрутов (приложение B) и по одному представителю на класс.
2. «Универсальный компаратор» для пути качества: элемент `(rank, id)`, `is_less` сравнивает только `rank`,
   ранги символьные. Любой strict weak order на ≤32 элементах есть ранжирование, поэтому ось F закрывается
   конструкцией, без generic-аргумента.
3. Шаг «код зависит от payload только через сравнения и предикаты размера/типа» — явно названный
   немеханизированный аргумент параметричности, а не theorem.
4. Механизированное ∀T — только VeriFast. Тогда и пилот из §6.3 должен отвечать на этот вопрос
   (generic T плюс спецификация замыкания), а не на «ownership вставки вообще».

### R6. Первой замкнутой композицией сделать полноразмерную, а не N4

N0/N1/N4 доказывают механизм, но не снимают главный риск. Стена одна: merge от 16 и `sort13`
(ваши POSTS8 и U64-N13 с TIMEOUT; #678 и #694 остановились там же). #701 в версии от 13 ноября заявляет, что прошёл
её модульно, ценой сотен корней и без подтверждения CI. До G4-2 нужны три одиночных замера:

1. `bidirectional_merge`, u8, len=32, sorted + probe-count, без panic-stub.
2. `sort13_optimal` через verified `swap_if_less`: sorted + count.
3. Consumer general N=32, где все вызовы заменены verified-stub'ами.

Каждый — одна строка CI. Они за день-два показывают, укладывается ли матрица в недели или нужен R7.

### R7. Loop contracts — сначала как средство удешевления внутри CAP=32, и сначала на merge

С учётом #701 это уже не запасной вариант, а главный способ отличиться: #701 закрывает merge примерно 125 корнями,
а вставку и swap — ещё почти двумя сотнями. Инвариант цикла сворачивает такую лестницу в несколько корней [гипотеза].
Пилот стоит запускать сразу, не дожидаясь исхода замера 1.

- Почему merge: он на каждом пути. В general merge нужен для каждой N от 2 до 32, в network — для 18..32,
  плюс merge на 8 внутри `sort8_stable` с 34 разными парами смещений (src, dst) в scratch при N=16..32
  (приложение A). Вставка даёт максимум 16 коротких итераций и, вероятно, дешёвая и без инварианта [гипотеза].
- Почему это лечит перестановку: счётчик по реальному телу — глобальное свойство мультиплексорной сети,
  для SAT оно тяжёлое. Инвариант делает его локальным: одна итерация переносит один элемент [гипотеза].
- Набросок инварианта merge — в приложении C: только граничные сравнения, развёрнутые предикаты
  с константной границей и счётчики. Z3 не нужен, #5148 не мешает.
- Доказательство одной итерации почти не зависит от смещений, поэтому заодно снимает проблему
  совпадения геометрии leaf и consumer.

### R10. Решить стратегию относительно #701

Это решение владельца; варианты не исключают друг друга.

- **A. Гонка за укладку в CI.** Выиграть можно не тем же способом позже, а меньшим числом корней: инварианты
  циклов для merge и вставки, consumer'ы с символьной N. Цель задаётся числом — десятки корней, а не сотни.
  Условие успеха: #701 не уложится в CI раньше.
- **B. Отличие по пункту 1.** Uninit-ON на реальных телах (C2/SEL1), судя по открытым PR, есть только у вас. Это сработает, если
  extra-UB флаги потребуют до приёмки #701; при этом v3risec чинит те же проверки upstream и его PR сливают быстро.
- **C. Совместное решение.** Правила не ограничивают число участников решения. Активы дополняют друг друга:
  его матрица и #5135; ваши #5153, CI-дисциплина, отрицательные контроли и uninit-инструментарий. Цена — делёж
  награды и координация; он может отказаться.

Моя оценка [суждение]: в чистой гонке A вы успеваете, только если #701 надолго застрянет на CI; B без A не
выигрывает; C заслуживает серьёзного рассмотрения именно потому, что каждая сторона уже зависит от фикса другой.
План пункта 2 в нынешнем виде не содержит ни одного из этих решений и рассчитан на темп, при котором #701
успевает раньше.

## 4. Дополнения

**A1. Первичный тип — u8.** Размер формулы растёт с шириной ключа; структура порядка на 32 элементах целиком
выражается в 8 битах. u8 попадает в те же маршруты, что u64 (network в T3, general с sort8 в T1).
i32/u64 оставить на граничных длинах для широты [гипотеза о стоимости — проверить одним замером u8 против u64].

**A2. Шесть тел, а не три имени.** У каждого trait по два impl. Примитивы достигают только Freeze/Copy-тел;
default-тела требуют `Cell<u8>` (!Freeze) и не-Copy обёртку. Контракт нужен на каждом из шести методов,
и каждый должен быть целью хотя бы одного `proof_for_contract` (в #5153 отдельно оговорено, что override
требует собственного контракта).

**A3. Символьная N вместо 66 строк.** Рецензент прямо просил harness'ы с символьной длиной. Если один harness
на маршрут дорог, делить по структурным классам: general — {0,1}, 2..7, 8..15, 16..32; network — {0,1}, 2..8,
9..12, 13..17, 18..24, 25, 26..32. Это 11 корней на тип.

**A4. Позиция 16 у insert_tail.** Network при N=17 вставляет на позицию 16 (sort13, затем позиции 13..16).
Сегодня её покрывает только u8-профиль (`contract_insert_tail_u8_prefix`, tail < 17). Контракт настоящего helper
(`insert_tail_contracts.rs`: tail 1..7 и 8..15) и u64-профиль (начало в индексе 1, tail 2..16) кончаются
на позиции 15 [факт]. Leaf, которым пользуются consumer'ы матрицы, должен включать 16.

**A5. Недостижимость `panic_on_ord_violation`.** Leaf merge под lawful-профилем должен доказывать её без
panic-stub; это отдельный критерий приёмки G4-2, в плане его нет.

**A6. Ограничения loop contracts на вашем же пине, не учтённые в таблице §5** [факт, по докам SEL1]:
- `loop_decreases` пересчитывает меру на каждой итерации, только если она читает переменные функции напрямую
  (`x`, `s.field`, `*p`); арифметика, приведения, индексация и вызовы считаются один раз до цикла (#4585, #3168).
  Меры из §4.2 («оставшееся число», «расстояние sift→begin») в таком виде не пройдут. Нужен ghost-счётчик
  либо отказ от termination: комитет его не просит.
- Квантифицированные предикаты с чтением через указатель **отвергаются** при `-Z uninit-checks` или
  `-Z valid-value-checks`. Инварианты для combined-ON должны быть бескванторными.
- `stub_verified` не переносит shadow-состояние. Значит, композиционная матрица — это профиль без extra-UB
  флагов, что совпадает с флагами организаторов.
- Нужна таблица «свойство → пин → набор флагов», иначе результаты двух профилей будут складываться по именам.

**A7. Три вопроса организаторам** (в #752 или #56; решение о публикации — за владельцем):
1. Подтвердить домен `len ≤ small_sort_threshold()` для трёх контрактов.
2. Нужна ли `insertion_sort_shift_left` за пределами длин вызывающих.
3. Допустимый бюджет времени и памяти CI; ожидаются ли extra-UB флаги в официальном прогоне.
К этому — просьба о бампе пина до коммита с #5153. #5148 открыт и взят в работу самим feliperodri,
так что упаковку Z3 чинить своими силами не стоит.

**A8. Обобщённость leaf-harness'а.** Kani не проверяет, что `proof_for_contract` покрывает весь `requires`.
Сделать это механическим: домен и геометрию писать в `requires` (нарушение ловится на месте stub'а),
а harness порождает все входы под `requires` — произвольные смещения в backing-массиве и обе топологии
(одна аллокация / разные). Плюс скрипт-инвентарь: каждый атрибут контракта имеет проверяющий корень
в обычном CI.

**A9. Устойчивость почти бесплатна на `(rank, id)`.** При `id` = исходный индекс выход stable-маршрута —
строгое возрастание по `(rank, id)` плюс сохранение ранга по id. Одно O(N)-условие даёт sortedness,
перестановку и устойчивость. Я прогнал настоящий код маршрутов нативно на 5,9 млн входов для всех N до порогов:
проверка совпадает со `sort_by_key` для general и fallback; network неустойчив начиная с N=9
(это тест, не доказательство). Устойчивость заявлять только для T1.

## Приложение A. Маршруты по длине (выведено из кода на `872d5a43`)

General (`small_sort_general_with_scratch`, `size_of::<T>() ≤ 16`):

| N | Примитив | Вставки (лев./прав.) | Merge |
|---|---|---|---|
| 0–1 | return | — | — |
| 2–7 | копия по одному | позиции 1..: от 0/0 до 2/3 | N |
| 8–15 | sort4 ×2 | позиции 4..: от 0/0 до 3/4 | N |
| 16–32 | sort8 ×2 (каждый: sort4 ×2 + merge 8) | позиции 8..: от 0/0 до 8/8 | N |

При `size_of::<T>() > 16` sort8 не используется: sort4 ×2 до N=32, до 12 вставок на половину.

Network (`small_sort_network`):

| N | Области | Merge |
|---|---|---|
| 0–1 | return | — |
| 2–8 | вставка от 1 | нет |
| 9–12 | sort9 + 0..3 вставки | нет |
| 13–17 | sort13 + 0..4 вставки (позиции до 16) | нет |
| 18–24 | две половины: sort9 + 0..3 | N |
| 25 | sort9 + 3 вставки и sort13 | 25 |
| 26–32 | две половины: sort13 + 0..3 | N |
| > 32 | abort | — |

Fallback: вставка от 1, позиции 1..15, N ≤ 16.

Набор leaf'ов для полной матрицы: `swap_if_less`; `sort4_stable`; `sort9_optimal`; `sort13_optimal`;

(scratch→v, v→stack scratch, внутри scratch для sort8). Наблюдаемый максимум сравнений в нативном прогоне:
general 252 при N=32, network 206 при N=32 и 103 при N=17, fallback 120 при N=16.

## Приложение C. Набросок инварианта `bidirectional_merge` (Kani не запускался)

Что проверено: пп. 1–6 выполняются на всех достижимых состояниях в 1,24 млн нативных прогонов настоящего
`bidirectional_merge` (len 2..32, половины упорядочены); индуктивность пп. 1–4 и условие выхода — полным перебором
для len ≤ 10 и алфавитов ключей из 2 и 3 значений (5 894 состояния, включая недостижимые, нарушений нет).
Индуктивность пп. 5–6 и выразимость в `loop_invariant` не проверялись.

`h = len/2`; после `k` итераций (`k = kani::index`): вперёд взято `i` слева и `j` справа, назад — `i′` и `j′`.
Сравнения — по ключу модели; половины входа упорядочены (предусловие, src не в `loop_modifies`).

1. Геометрия: `left = src+i`, `right = src+h+j`, `left_rev = src+h−1−i′`, `right_rev = src+len−1−j′`;
   `i+j = k = i′+j′`.
2. Непересечение: `i+i′ ≤ h`, `j+j′ ≤ len−h`.
3. Взятое вперёд — префикс стабильного порядка:
   `(i=0 ∨ h+j=len ∨ key(src[i−1]) ≤ key(src[h+j]))` и `(j=0 ∨ i=h ∨ key(src[h+j−1]) < key(src[i]))`.
4. Взятое назад — суффикс:
   `(i′=0 ∨ j′=len−h ∨ key(src[h−i′]) > key(src[len−1−j′]))` и
   `(j′=0 ∨ i′=h ∨ key(src[len−j′]) ≥ key(src[h−1−i′]))`.
5. Выход: `dst[0..k)` и `dst[len−k..len)` упорядочены (развёрнутый предикат, граница 32);
   при `k>0` элемент `dst[k−1]` равен `src[i−1]` или `src[h+j−1]`, а `dst[len−k]` — `src[h−i′]` или `src[len−j′]`.
6. Кратности: `count(p, dst[0..k)) = count(p, src[0..i)) + count(p, src[h..h+j))`, симметрично для суффикса.

Шаг: при совместном исчерпании левой половины (`i+i′ = h`) из п. 4 и упорядоченности правой половины следует
`key(src[i]) > key(src[h+j])`, то есть вперёд берётся правый элемент и п. 2 сохраняется; симметрично для правой.
На выходе из пп. 1–2 получается `i+i′ = h`, `j+j′ = len−h` (для нечётной длины — ровно один остаток),
поэтому ветка `panic_on_ord_violation` недостижима; стык упорядочен по пп. 3–5; перестановка — по п. 6.
