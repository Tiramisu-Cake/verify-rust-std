## Зачем

DIRECT доказал u64 N6..8 (B: N6 235 с / 6,0 GiB, N7 383 с / 6,3 GiB, N8 TIMEOUT; A: N6..8 310–418 с / 6,6–8,8 GiB),
но пики 6–9 GiB на GCB — сильный риск для CI организаторов (пригодность на macOS не измерена): `kani_autoharness` — `--jobs=3`, 600 с на гармонику; macOS
`macos-latest` (по документации GitHub около 7 GiB). Гипотеза (не установлена): каждая гармоника сейчас держит в одной
формуле обе ветви (`stable` symbolic: general и stable маршрут; у A — две backing-аллокации); раздельные гармоники
снизят пик одной проверки. Суммарное время может вырасти — это допустимо.

## Что сделать

- **B-split:** для u64 N6 и N8 — по две гармоники (по умолчанию opt-in под `cfg(kani_smallsort_controls)`; в ordinary
  переводит только координатор по результатам): только `small_sort_general` и только
  `StableSmallSortTypeImpl` с `[MaybeUninit<T>;48]`; каждая создаёт только своё scratch. Внутреннего symbolic `stable` быть не должно:
  вызвать прежний helper с оставшимся случайным selector недостаточно. Тот же
  `assert_sorted_and_probe_preserved`, `set_value_probe`, `lt_u64`, `unwind(34)`, flags; без stubs.
- **A-split:** для u64 N6 и N8 — по две `proof_for_contract(bidirectional_merge)` (тоже opt-in): только `MaybeUninit<[T;48]>`
  (general) и только `[MaybeUninit<T>;48]` (stable); каждая создаёт только свою backing-аллокацию. Префикс N
  инициализирован, хвост uninit, отдельный инициализированный dst, прежние requires/modifies; arbitrary значения/probe,
  comparator и frame сохранить.
- Обосновать по коду, что объединение раздельных гармоник = домен исходной (ветви, аллокации, значения, covers).
  Covers: по одному на гармонику, SATISFIED. Новые контроли не нужны, если oracle/контракт не меняются; если меняются —
  контроль обязателен.
- Ensures/oracle/домены/flags не ослаблять, timeout не повышать. Эквивалентная специализация oracle (typed probe и т.п.)
  в этой сессии — только как письменное предложение, не код.
