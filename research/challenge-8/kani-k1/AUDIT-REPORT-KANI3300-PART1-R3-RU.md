# Независимый аудит Kani #3300 Part 1, раунд 3

**Дата:** 13 ноября 2026 года. Бриф: [`AUDIT-BRIEF-KANI3300-PART1-R3.md` @ `385b2e02b1`][brief]. Семантический кандидат: [`4f64cc617c`][cand], tree `af28e22ec446b254cfa3a28b2882eafa58d5a458` (совпадает с брифом, проверено по checkout).

**Вердикт.** Сужать scope сейчас не следует. По имеющимся данным ресурсный блокер PFC + uninit не связан ни с протоколом A3, ни с представлением buffer:

- размеры формул четырёх завершённых прогонов с точностью до 0,2 % равны целому числу чтений таблицы объектов DFCC из 2^object_bits элементов;
- все 18 сопоставимых вариантов таблицы §7.1 брифа делятся одним признаком: лежит ли transfer-buffer внутри DFCC frame;
- блокер измеряли только при Kani-default `--object-bits 16`. Verify-std workflow upstream и runner организаторов Challenge 8 работают при 12; в отдельных собственных contract-тестах upstream сам снижает значение до 8–12.

Первый шаг — пересчёт по уже сохранённым потокам и журналам, без запусков. Второй — P1/P2 на штатных бинарниках, без патчей: при меньшем числе object bits и, отдельно, без formula slicing. Guard G-SC привязан к эффекту (shadow transfer), который расход не определяет; реализовывать его не рекомендую.

Семантическая цепочка A1–A3R + B1I + M1 + S3 по чтению кода согласована для заявленных форм. Экспорт блокируют отсутствующие свидетельства: нет ни одного положительного результата легального PFC с shadow transfer, нет ни одного теста Replace или RecursiveCheck под uninit-checks, не выполнены M3 и полный gate.

## 2. Ресурсный блокер: что на самом деле измеряли

### 2.1. Шесть фактов из исходников

1. **Таблицы DFCC.** Каждый write set содержит три множества, индексируемые номером объекта: `contract_frees`, `allocated`, `deallocated`. Размер каждого — `1UL << object_bits` указателей, память выделяется `__CPROVER_allocate` константного размера. [Создание][c-objset] · [write set][c-wscreate]. Число object bits CBMC берёт из своей командной строки и [пересчитывает][c-maxmalloc] под него `__CPROVER_max_malloc_size` при загрузке модели. При Kani-default [16][k-objbits] таблица занимает 65 536 × 64 = 4 194 304 бита.
2. **Flattening.** Поле `unbounded_array` по умолчанию равно `U_NONE`. Фабрика решателя меняет его только для `--arrays-uf-never` и `--arrays-uf-always`; `U_AUTO` с порогом `MAX_FLATTENED_ARRAY_SIZE` не выставляется нигде. Массив константного размера всегда разворачивается в биты целиком. [Default][c-unbounded-h] · [предикат][c-unbounded] · [фабрика][c-factory]. «Capacity 4 194 304 bits» из D1 — фактическая ширина операнда, а не оценка сверху.
3. **Где таблица читается и пишется.** DFCC [проверяет][c-lhs] каждую запись через разыменование или в нелокальный объект. Проверка исполняет `if(set->allocated.elems[__CPROVER_POINTER_OBJECT(ptr)] != 0) return 1;` — [строка 818][c-check]. Таблица `allocated` обновляется на DECL и DEAD каждой [отслеживаемой][c-tracked] локальной, то есть локальной со взятым адресом: [`add_decl`][c-adddecl], [`record_dead`][c-dead].
4. **Цена чтения.** Индекс `POINTER_OBJECT(&X)` синтаксически не константа, поэтому [`convert_index`][c-index] идёт общей ветвью: для каждого из N элементов строит [`land`][c-land] из W равенств бит, причём раньше, чем выясняется, что литерал сравнения индекса равен константе false. Если биты массива — константы, чтение стоит ровно N + W переменных и N·(W + 1) + 1 клауз. Если биты массива — свободные переменные, добавляются W·N XOR-вентилей: 129·N + W переменных и 321·N + 1 клауз.
5. **Symex это чтение не сворачивает.** `ARRAY_OF(NULL)` распространяется как константа, и чтение из него [упрощается][c-arrayof]. После первой записи значением становится `WITH`, а `WITH` symex [не распространяет][c-prop].
6. **Slicer и GOTO.** [`symex_slicet`][c-slice] сначала игнорирует всё, что стоит после последнего утверждения, затем собирает зависимости только из ASSERT, ASSUME и правых частей удержанных присваиваний. Шаги GOTO до последнего утверждения он не помечает и зависимостей из них не берёт. [`convert_goto_instructions`][c-goto-conv] конвертирует условие каждого неигнорированного GOTO; условие записано в шаг в L2-форме, вместе с чтением массива ([symex][c-symex-goto]). [`show_program`][c-show] шаги GOTO не печатает. Символ массива без удержанного определения получает [свежую переменную на каждый бит][c-map]. Утверждение, условие которого свернулось в true, symex в уравнение [не записывает][c-vcc].

| object bits | N | Чтение удержанной таблицы: переменные / клаузы | Чтение срезанной таблицы: переменные / клаузы |
|---:|---:|---:|---:|
| 16 | 65 536 | 65 600 / 4 259 841 | 8 454 208 / 21 037 057 |
| 14 | 16 384 | 16 448 / 1 064 961 | 2 113 600 / 5 259 265 |

Конвертер кэширует результат по выражению, а `POINTER_OBJECT(&x.f)` упрощается до `POINTER_OBJECT(&x)`. Поэтому платится каждое *различное* чтение: пара «версия таблицы, корневой объект». Правая колонка — первое чтение версии; повторное чтение той же срезанной версии по другому объекту добавляет 65·N + W переменных и те же клаузы.

### 2.2. Арифметика четырёх завершённых прогонов

Счётчики взяты из §7.1 брифа; время Convert SSA — из §2.2 [отчёта PFC-resource][pfc], в таблице оно поделено на k.

|---|---:|---:|---:|---:|---:|---:|---:|
| upstream, 43253856019 | 284 883 | 17 072 414 | 4 | 22 483 | 33 050 | 99,81 % | 0,74 |
| V02, 43258921276 | 844 029 | 51 222 776 | 12 | 56 829 | 104 684 | 99,80 % | 0,71 |

| R6-02b, 43276309576 | 829 958 | 51 173 785 | 12 | 42 758 | 55 693 | 99,89 % | 0,79 |

Здесь k = ⌊клаузы / 4 259 841⌋, остаток — то, что не объясняется k чтениями. Совпадение идёт по двум независимым счётчикам во всех четырёх прогонах; при k + 1 остаток клауз становится отрицательным. Собственно программа P1 в этих формулах занимает 23–60 тыс. переменных и 33–105 тыс. клауз.

Отсюда три следствия.

- «Рост 17M → 51M» — это переход от 4 чтений к 12. О сложности compiler delta R1 он не говорит ничего.
- Отношение клауз к переменным ≈ 60 во всех четырёх прогонах — подпись вентиля `land` на 64 входа. Это видно без профилировщика.
- Сигнатура соответствует именно ветви `prop.has_set_to()` с константным сравнением индекса: при символьном индексе на элемент приходилось бы не одна, а три переменные.

Прямого профиля конвертера нет, поэтому статус этого пункта — «установлено арифметикой», а не «измерено».

### 2.4. Гипотеза Г1: почему легальный прогон тяжелее нелегального

**Что следует из исходников и сводки D1.** В легальном прогоне каждая запись shadow runtime в `MEM_INIT_STATE` проходит frame check: цель есть в assigns. В [сводке D1][d1sum] для R1+skip результат проверки виден как `__check_lhs_assignment == TRUE` и срезан; записей `ASSERT(__check_lhs_assignment…)` там нет. Утверждение с условием true в уравнение не попадает (факт 6). Slicer поэтому не имеет ни одной зависимости от таблицы и срезает все её обновления: у R1+skip удержано 0 из 85 `WITH` и 0 из 12 `ARRAY_OF`. Шаг GOTO той же проверки остаётся: он стоит раньше последнего утверждения прогона, проверки в ensures, и потому конвертируется. Его условие читает версию таблицы без определения, конвертер выделяет под неё 4 194 304 свежие переменные и строит чтение по правой колонке таблицы из §2.1.

В прогоне с нарушением frame запись в buffer даёт нетривиальное утверждение, зависящее от таблицы. У R6-02b в той же сводке удержаны 11 `ASSERT(__check_lhs_assignment…)` в `store_argument` и `load_argument` и цепочка `dynamic_object$12#2 … #14` без пропусков: восемь `add_decl` (`var_0`, `var_3`, `var_4`, параметры `a` и `b` функции `select`) и пять `record_dead`. Биты удержанной таблицы — константы, и каждое чтение стоит «дешёвые» 4,26 млн клауз. Срезанных чтений в завершённых прогонах нет вовсе: переменных меньше миллиона.

Параметры `a` и `b` попали в таблицу потому, что uninit-инструментация берёт их адрес для Load. Она же добавляет в extent проверяемые записи в `MEM_INIT_STATE`. Поэтому механизм включается именно под `-Z uninit-checks`, хотя сам принадлежит DFCC.

**Что оценено, а не измерено.** Число D различных чтений срезанных версий в P1 и память на одно чтение.

- У R6-02b удержано 13 обновлений таблицы, а различных чтений 12. Если у легального R1+skip чтений столько же и каждое идёт по своей срезанной версии, его формула при 16 битах — порядка 250 млн клауз и 100 млн переменных. При 12 битах та же формула — около 16 млн клауз и 6 млн переменных.
- Одно такое чтение при 16 битах — 21 млн клауз и 8,45 млн переменных. При ~40 байтах на клаузу, как у R6-02b, и ~100 байтах на переменную это 1,5–2 GiB. Вторая цифра — допущение. Watchdog 6 GiB тогда соответствует трём-четырём чтениям.

Что поддерживает Г1 помимо сводки D1:

- **Скорость роста памяти.** Убитые прогоны занимают 6,4–8,6 GiB за 9–11 с работы: 0,6–0,9 GiB/с. R6-02b за всё время, включая solver, занял 1,86 GiB, а его Convert SSA длился 9,5 с: не более 0,2 GiB/с. Убитые прогоны — не «те же клаузы, но больше». У срезанного чтения на клаузу приходится 0,4 новой переменной против 0,015 у удержанного.
- **Единственный легальный PFC-корень, дошедший до вердикта.** Первый memprobe шёл без watchdog на 16-GB runner: `legal-pair` (два корня, тяжёлый — PFC) — 14:16 мин и ≈ 14,4 GiB (15,07 «GB» в прежней подписи), `postcondition-hole` убил runner. У R6-02b с нарушением frame — 50 с и 1,86 GiB.
- **Разбиение из §2.3** без исключений.
- **Тесты кандидата.** Кандидат добавляет четыре PFC + uninit теста. Два остались в дереве restricted Quick (135/0): [`maybe-uninit-contract-frame`][k-test-frame], где тело после transfer пишет вне frame, и [`maybe-uninit-contract-clause`][k-test-clause], где проверяемое тело пусто. Два легальных — [`legal-pair`][k-test-legal] и [`postcondition-hole`][k-test-hole] — убраны из CI из-за ресурса. Состав selectors Quick по журналам я не перечитывал.
- **Symex-only** на тех же моделях занимает 0,9 с и 36–39 MiB: всё происходит в конверсии.

Поправка к D1. Вывод «большой backing есть у дешёвого контраста, поэтому это не объяснение OOM R1» обратен действительному: контраст дёшев потому, что его backing удержан и константен. «Offender не найден» — свойство инструмента: `--program-only` не показывает шаги GOTO, а деление на retained и sliced не описывает то, что конвертер обрабатывает помимо slicer. Из непечатаемых классов шагов чтение таблицы несут только условия GOTO.

### 2.5. Upstream уже знает этот класс; профиль организаторов — 12 бит

- [`tests/expected/function-contract/history/stub.rs`][k-test-stub]: комментарий «consumes > 9 GB of memory with 16 object bits», object bits снижены до 8. В файле два PFC-корня: `*ptr += *ptr` и функция, дважды вызывающая первую через `stub_verified`.
- [`…/interior-mutability/whole-struct/refcell.rs`][k-test-refcell]: object bits снижены до 12 до исправления kani#3611.
- Ещё два теста loop contracts идут при 8 битах. Остальные 125 из 127 contract-тестов upstream идут при 16: класс проявляется не на каждом PFC, а там, где в extent есть и отслеживаемые локальные, и проверяемые записи после них.
- Workflow [`verify-std-check.yml`][k-verifystd] и [`scripts/run-kani.sh`][runkani] этого репозитория запускают Kani с `--cbmc-args --object-bits 12`. [RESULT-DIRECT][direct] фиксирует тот же профиль для SmallSort.
- PFC под `-Z uninit-checks` в upstream покрыт двумя местами, оба при 16 битах: пакет [`tests/std-checks/std`][k-test-stdchecks] (`Box::from_raw`, `Atomic*::from_ptr`) и [`verify_std_cmd`][k-test-verifystd] (`fake_function`, `add_one`). By-value `MaybeUninit` или union через границу вызова в них нет.

P1/P2 во всех стадиях запускались одиночным `kani` без `--cbmc-args`, то есть при 16 битах; D1 это подтверждает ([ATTRIBUTION][d1attr]: `nof_objects 65536`). В заданиях R2–R6b и D1 object-bits прямо предписано не менять. Параметр, который upstream снижает именно для contract-тестов, не варьировался ни разу.

Снижение object bits не меняет семантику: это ёмкость кодирования указателя. При нехватке CBMC завершается явной ошибкой [`too many addressed objects`][k-objbits-test].

### 2.6. Проверка Г1

**Шаг 0, без запусков.** Два пересчёта по уже имеющимся данным.

По сохранённым потокам D1 (`--program-only`, оба случая) посчитать различные пары «версия таблицы `dynamic_object$m#j`, индекс» для трёх таблиц write set. Считать до последней записи ASSERT в потоке: в guard-присваиваниях `\guard#N == …`, удержанных и срезанных, и в удержанных прочих присваиваниях. Каждое такое guard-присваивание — зеркало условия GOTO, которое конвертер обработает. Предсказания:

- R6-02b: 12, то есть k из §2.2. Это независимая проверка модели чтений. Расхождение покажет, какие чтения модель не учла.
- R1+skip: D порядка десяти, и ни одна прочитанная версия не имеет удержанного определения. Нижняя оценка формулы R1+skip тогда D × 21 037 057 клауз. D = 0 опровергает Г1 без единого запуска.

В журнале первого memprobe 43232249168 найти счётчики CNF корня `legal_pfc_transfer`, если они попали в вывод. Это единственный легальный PFC-корень, дошедший до solver. Предсказание: десятки миллионов переменных и отношение клауз к переменным от 2,5 до 5, а не около 60.

**Шаг 1, штатные флаги.** Вход: `4f64cc617c`, неизменные P1/P2 (хэши из брифа), одиночные корни, прежние лимиты 300 с и 6 GiB. Источник не меняется.

| Плечо | Флаги сверх `-Z uninit-checks -Z function-contracts` | Предсказание Г1; ориентир при D ≈ 12 |
|---|---|---|
| A | — (16 бит) | KILL; уже есть, повторять не нужно |
| B | `-Z unstable-options --cbmc-args --object-bits 14` | На границе лимита: ≈ 63 млн клауз, ≈ 25 млн переменных |
| C | то же, `--object-bits 12` | Завершение: ≈ 16 млн клауз, ≈ 6 млн переменных, порядка 1–1,5 GiB |
| D | то же, `--object-bits 10` | Завершение: ≈ 4 млн клауз, ≈ 1,6 млн переменных |
| E | то же, `--object-bits 8`, если хватает объектов | Завершение |
| F | как C, плюс `--no-slice-formula` | Различающее. Переменных меньше, чем в C, хотя slicing выключен: на чтение приходится ≈ 4 тыс. вместо ≈ 0,53 млн |
| G | `-Z unstable-options --no-slice-formula` (16 бит) | По Г1 может завершиться: клаузы ≈ k′ × 4 259 841 + r. Уложится в 6 GiB при k′ до ~35 |
| H | `-Z unstable-options --cbmc-args --arrays-uf-always` | Вспомогательное. В счётчиках нет кратных 2^16. CBMC может отвергнуть модель в этом режиме по посторонней причине; тогда не интерпретировать |

Плечи F и G опираются на то, что без `--slice-formula` CBMC [выполняет][c-slice-opt] только simple slicing после последнего утверждения; Kani передаёт `--slice-formula` [по умолчанию][k-slice-flag]. Все версии таблицы тогда удержаны, и каждое чтение «дешёвое». Число чтений k′ при этом больше k: добавляются чтения внутри самих `add_decl` и `record_dead`, которые slicer обычно срезает. Любая гипотеза о тяжёлом удержанном терме предсказывает для F обратное: без slicing формула только растёт.

Если при 10 или 8 битах CBMC сообщает о нехватке объектов, плечо пропускается: для прямой достаточно двух точек, третья её проверяет.

Сигнатуры в плечах B–E. Счётчики ложатся на прямые по 2^bits с общими коэффициентами: клаузы = A·2^b + r, переменные = B·2^b + r′. По Г1 A = 321·D + 65·C при целых D ≥ 1 и C ≥ 0, где D — число чтений срезанных версий, C — удержанных; отношение A/B лежит между 2,5 и 5, а не около 65.

Семантический oracle тот же: P1 — SUCCESS; P2 — ровно одно упавшее свойство, uninit read в ensures. Любой исход плеч C–E впервые даёт завершённый результат по легальному PFC на `4f64`: либо SUCCESS, либо конкретный список отказов.

Для каждого плеча сохранять: object bits, steps, VCC до и после упрощения, переменные, клаузы, время Convert SSA, maxrss в KiB, exit или signal, полный список свойств. Хвост журнала, а не первые 30 строк: это замечание прежнего аудита остаётся в силе.

Правило решения.

- **Г1 подтверждена**, если C и D завершаются, счётчики линейны по 2^bits, A/B < 10, экстраполяция на 16 бит даёт десятки миллионов переменных, а в F переменных меньше, чем в C. Блокер тогда переклассифицируется как масштабирование DFCC по object bits, класс kani#3611, и перестаёт быть вопросом дизайна Part 1.
- **Г1 опровергнута**, если C и D тоже не завершаются, либо счётчики не зависят от bits, либо экстраполяция на 16 бит даёт формулу порядка завершённых прогонов (≈ 51 млн клауз, меньше 1 млн переменных). Следующий шаг тогда описан в ответе 5; G-SC и в этом случае не выдаётся, пока причина неизвестна.

Семантический исход оценивается отдельно: неожиданный FAIL в P1 при подтверждённой Г1 — самостоятельная находка, а не довод против неё.

## 3. Ответы на вопросы брифа

### 1. Минимальный корректный и полезный объём; сужать ли сейчас

Не сужать. Минимальный полезный объём — текущая семантика `4f64` целиком: direct MU и flat slots, bytewise и typed transfer, протокол A3, B1, full-extent `raw_eq` с M1, S3, явные Unsupported там, где они стоят. PFC остаётся поддержанной семантикой с документированным ресурсным ограничением DFCC при 16 object bits.

Причина. G-SC превращает P1/P2 в Unsupported и отнимает практическую цель, а признак, по которому он режет, расход не определяет (§2.3). Scope cut, построенный на неверной причинной модели, пришлось бы потом и расширять, и отзывать.

Чтобы объём можно было *заявить*, нужны: завершённые P1, P2, `legal-pair`, `postcondition-hole` (при сниженных object bits — допустимо, см. ответ 12); M3; решение по Replace и RecursiveCheck (квалифицировать либо явно не заявлять); полный regression gate.

### 2. Если всё же сужать — где честная граница

Не между transfer и не-transfer. DFCC применяется только к harness с `proof_for_contract` либо с достижимыми loop contracts при `-Z loop-contracts` ([условие][k-dfcc-flag] · [вызов][k-dfcc-driver]). Ordinary, Assert и Replace в обычном `#[kani::proof]` через DFCC не проходят, ресурсный класс их не касается.

Внутри PFC write set активен только в теле modifies-wrapper. `requires` и `ensures` Kani вычисляет в check-closure, снаружи: в golden frame-теста место отказа — `frame_target::{closure#2}::{closure#0}`. Чтение hole в ensures у P2 лежит вне DFCC extent; тяжёлая часть — проверяемые shadow-записи внутри тела, включая Store0 на его возврате. Setup harness тоже снаружи.

Effect-based guard по shadow transfer не необходим и не достаточен. Не необходим: для P1/P2 дело не в transfer. Не достаточен: по Г1 PFC над scratch без единого by-value transfer — raw-указатели плюс локальные со взятым адресом плюс shadow-записи `set_ptr_initialized` — попадает в тот же механизм, а guard его пропустит. Это прямо касается SmallSort: helper-корни получают scratch указателями.

Ограничить расход способен только отказ на входе modifies-wrapper, то есть «PFC + uninit не поддержан целиком». Это и есть практическая цель. Честная формулировка границы — ресурсное ограничение с рекомендацией по object bits, а не Unsupported: семантика при этом цела, решение обратимо и совпадает с практикой upstream.

### 3. Достаточны ли D1 bindings; что значимо

Сами по себе недостаточны: инструмент не видит шаги GOTO. Вместе с исходниками CBMC и счётчиками CNF они дают конкретную различающую гипотезу (§2.4).

- **Цепочка 1** (R1, phi `saved_object_id`, PC 664): для стоимости незначима. Это 64-битное равенство и мультиплексор, сотни клауз.
- **Цепочка 2** (R6, frame check PC 628–631): значима как причина *удержания* таблицы, не как расход.
- **Цепочка 3** (R6, `allocated`): ключевая, но прочитана наоборот.

По ширинам. Boolean root width действительно ничего не говорит. Storage 56 B, 32 B и `Layout<1>` к расходу отношения не имеют. Значима ширина операнда `dynamic_object$12`, 4 194 304 бита — фактическая, а не «capacity». Значимая multiplicity — число различных пар «версия таблицы, объект» среди чтений, а не число `WITH` и не число occurrences. В завершённых прогонах она читается из счётчиков: k.

### 4. Предупреждения `saturating_add/sub` и abort paths в R6

**Saturating.** Механизм следует из исходников и к Part 1 отношения не имеет. `enter_contract_clause` и `exit_contract_clause` экспортированы как `__VERIFIER_kani_*` и вызывают `usize::saturating_add/sub` — [lib.rs:823–846][k-clause-depth]. DFCC не инструментирует функции с префиксом `__VERIFIER` и не правит их call sites ([предикат][c-verifier] · [пропуск][c-other]). Вызываемый `saturating_add` при этом инструментирован и получил в конец списка параметр `__write_set_to_check` ([добавление][c-addparam]). Symex видит на один аргумент меньше и [подставляет nondet][c-notenough] — именно для write set. Операнды `self` и `rhs` связаны корректно.

Последствие сейчас нулевое: тело `saturating_add` не содержит проверяемых записей и отслеживаемых локальных, указатель не разыменовывается. На арифметику, пути и расход предупреждение не влияет. Отдельный fidelity-repro перед ресурсными сравнениями не нужен. Достаточно сверить в уже сохранённых stdout, что source location предупреждений — `library/kani_core/src/lib.rs:833` и `:846`. Наверх стоит отправить небольшое замечание: непроинструментированная функция вызывает проинструментированную.

**Abort paths.** Строка `aborting path on assume(false)` — сообщение уровня statistics. Оно печатается, когда symex встаёт на инструкцию, условие которой *синтаксически* равно false, а guard пути синтаксически не false ([код][c-abort]). Достижимость пути оно не устанавливает. В R6 это ветвь `otherwise` разбора `if let Some(buffer) = ARGUMENT_BUFFER` и panic-ветвь `assert!`. Источник символьного дискриминанта: DFCC перед стартом [хавочит статики][c-nondet], а после первого demonic store дискриминант символьный по построению. Fidelity-дефекта здесь нет.

Сравнивать R1 и R6 как ресурсные baselines нельзя по другой причине — §2.3.

### 5. Минимальная следующая диагностика

Stock-данные и stock-флаги, без патча CBMC.

0. **Без запусков.** Оба пересчёта шага 0 из §2.6 и сверка source location предупреждений saturating (ответ 4).
1. **Пакет из §2.6.** Причинным его делают два свойства: меняется один параметр кодирования при неизменных source и input, и предсказан закон масштабирования, а не просто «станет легче».
2. **Только если шаги 0–1 противоречат Г1.** На сохранённой actual-модели R1+skip запустить штатный `cbmc` с её же argv плюс `--verbosity 10`, под прежним лимитом, сохранив *хвост* вывода. `convert_goto_instructions` и остальные фазы на debug-уровне печатают шаг до вызова конвертера, так что последняя строка перед kill называет шаг-виновник. Это та самая запись «enter до аллокации», ради которой предлагался патч C. Запускать прямым вызовом `cbmc`, как в D1-P, чтобы argv и поток вывода были под контролем.

`scripts/profile_cbmc.py` по существу достаточен: flamegraph показал бы `convert_goto_instructions → convert_index` против `convert_assignments → convert_with_array`. Первым шагом я бы его не брал: нужны `perf` с правами на runner и бинарник с символами, то есть фактически сборка CBMC. Шаги 0–1 дешевле и различают сильнее.

Bounded patch C не нужен, пока шаги 0–2 не исчерпаны.

### 6. Узкая оптимизация на `4f64` или другой протокол

Другой протокол не нужен: данных, которые относили бы расход на A3, snapshot или carrier, нет. Варианты ниже не трогают pre-Move snapshot, pairing, return0, маски M1, S3 и пользовательские frame checks.

1. **Флаги, без изменения source.** PFC + uninit запускается при сниженных object bits. Профиль организаторов уже на 12. Хватит ли 12 для реального scratch, из P1 не следует: цена растёт с числом различных чтений, а оно — с числом записей и отслеживаемых локальных в extent. Это покажут плечи B–E и replay. Если подтвердится плечо F, второй рычаг — `--no-slice-formula`: по Г1 каждое чтение становится впятеро дешевле по клаузам и на два порядка по переменным, ценой неслайсенной остальной формулы.
2. **Kani: вывести shadow runtime из-под инструментации DFCC.** Записи `mem_init` касаются только `MEM_INIT_STATE` и собственных локальных; пользовательские указатели там только измеряются. Если DFCC эти функции не инструментирует, проверок на shadow-записях нет вовсе и запись `MEM_INIT_STATE` в assigns не нужна. Чтения таблицы, связанные с shadow-записями, тогда исчезают; остаются чтения пользовательских записей, как без uninit. Прецедент есть в самом upstream — `__VERIFIER_kani_enter_contract_clause` и комментарий к [`SKIPPED_ITEMS`][k-skipped]. Ограничения:
   - модели generic, `export_name` к ним неприменим, нужна схема имён в codegen;
   - вызовы из них проинструментированных `any`, `to_raw_parts`, `wrapping_sub` дадут тот же nondet write set, что в ответе 4, — их надо заменить intrinsic-ами либо проверить поимённо;
   - локальные непроинструментированной функции не отслеживаются, поэтому передавать их адрес проинструментированному callee нельзя;
   - исключение должно определяться идентичностью функции Kani, а не именем, которое может выбрать пользователь.

   Это изменение trusted semantics: по вашим правилам нужны rationale и trust review до реализации.
3. **CBMC: устранить причину.** Три независимые точки. (а) В `convert_index` не строить `land` для индекса, чьё сравнение константно ложно, либо брать ветвь константного индекса, когда биты индекса константны. (б) Не конвертировать условие GOTO, символы которого не имеют удержанных определений; `cond_handle` шага GOTO нужен только [для трассы][c-trace]. (в) Не делать таблицы DFCC развёрнутыми массивами на 2^object_bits. Пункт (а) уменьшил бы и «дешёвые» 4,26 млн клауз до десятков, то есть ускорил бы все PFC, включая ваши uninit-off прогоны. Требуется сборка CBMC; это отдельный upstream-трек.

До проверки Г1 реализовывать не следует ни один из трёх. Пункты 2 и 3 — предложения, не измеренные исправления.

Расширять assigns до отдельных ячеек (R7 B1: 12 targets, R8: 13) контрпродуктивно. Soundness это не добавляет, а каждая проверка обходит весь список целей; рост steps с 11 700 у R7 B0 до 18 099 у R7 B1 с этим согласуется.

### 7. Если guard оправдан: context, полнота, cache

Сейчас не оправдан. Технически:

- **Context выбранного harness** уже есть на уровне codegen unit. Unit'ы группируются по ключу «contract usage, stub map» ([`group_by_stubs`][k-units]), у каждого unit свой `BodyTransformation` ([создание][k-transformer]), а `FunctionWithContractPass::new` выводит `check_fn` и `replace_fns` из harness этого unit ([конструктор][k-contract-pass] · [mode][k-mode]). Тот же `check_fn` можно передать в `UninitPass`. Ordinary и PFC корни одной функции оказываются в разных unit'ах с разными кэшами, так что перенос отказа между ними исключён конструктивно.
- **Полнота closure** требует достижимости от modifies-wrapper по *трансформированным* телам. У per-instance `TransformPass` её нет; это `GlobalPass` по образцу [`DelayedUbPass`][k-delayed], у которого есть `call_graph`, `instances` и `transformer`.
- **B1 и остальное.** Если visitor не трогать, а Unsupported ставить одним check на входе wrapper, диагностика B1, return-only, generic и generated closures не теряются. Неразрешённые рёбра уже обрываются Unsupported локального visitor.
- **T1b** — отдельно. `DelayedUbPass` пишет инструментированное тело обратно в общий кэш unit'а ([запись][k-delayed]). Это перенос между harness одного unit, а не между ordinary и PFC.

### 8. Отказ до partial transfer и до дорогого prefix

Гарантию даёт только вход modifies-wrapper: Unsupported раскрывается в assert + `assume(false)`, symex дальше не идёт, проверяемых записей и чтений таблицы не возникает. Guard «перед первым transfer» поздний: shadow-записи до него уже оплачены.

Compile-time отказ ресурс тоже снимает, но ошибкой компиляции быть не должен — при `verify-std` он остановит сборку всего crate. Последствия whole-harness cut: P1 и P2 становятся Unsupported; `stub_verified` на тот же контракт теряет основание, потому что stub, чей PFC не доказан, не verified; практическая цель scratch-PFC закрывается.

### 9. Replace, stub_verified и приватные записи

**Whole-state assigns сохранить.** Это upstream-механизм, а не часть Part 1: `codegen/contract.rs` относительно base не менялся ([код][k-contract-assign]). Он добавляет в assigns один приватный статик и не разрешает ни одного пользовательского pointee. Точная классификация ячеек ничего не добавляет и удорожает каждую проверку (ответ 6).

**Исправить.** Поиск маркированного статика заканчивается `unwrap_or_default()` — [строка 170][k-contract-assign]. Если символа нет, assigns молча остаётся без приватного состояния, и shadow-записи дадут frameFAIL. Это fail-closed, но по §2.4 заодно маскирует ресурсную картину. При включённых uninit-checks и достижимых shadow-операциях отсутствие символа должно быть явной ошибкой.

**Replace не квалифицирован совсем.** В дереве кандидата ноль тестов со `stub_verified` или `kani::recursion` под uninit-checks. По чтению кода:

- By-value shadow return в replace-closure идёт через `kani::any_modifies`, то есть через `kani::any`. `Arbitrary for MaybeUninit<T>` недетерминированно возвращает `new(T::any())` либо `uninit()` ([impl][k-arbitrary]). Это правильное демоническое поведение, если transfer через `any` спарен. Теста нет.
- `ensures`, читающий payload, в Replace вычисляется под `assume`. Uninit check в `UninitPass` — assert без assume ([порядок passes][k-order]), поэтому на ветви `uninit()` он сработает раньше, чем assume её отсечёт. Ожидаемый результат — ложный FAIL у любого stub с таким ensures. Нужен тест и решение: документировать либо в Replace считать проверки clause допущениями.
- Hooks, которые backend подставляет вместо тела, протокол не спаривают. Caller получит `missing shadow transfer protocol`. Это fail-closed, но его надо зафиксировать тестом или явным Unsupported.

Пока этого нет, Replace и RecursiveCheck с shadow-значениями в заявление Part 1 не входят, и это должно быть написано явно.

### 10. Закрыты ли findings R2; что остаётся

Закрыто для заявленных форм, по чтению диффов и прогонам из брифа:

- **Блокер `raw_eq`.** D0 диагностировал promoted immutable RHS. M1 сеет маску по фактическим байтам allocation, `None` остаётся false. Допуск узкий: shared-ссылка на всю allocation, `Freeze`, поддержанный тип, без relocations ([`frozen_origin`][k-anon] · [`admitted`][k-immut]). Вне допуска значение остаётся false. Неоправданного bless в модели я не нашёл.
- **B1.** Один обход и один flush, общий `resolve_call`, guard на отсутствующее тело в points-to. Поведение совпадает с описанием.
- **S3.** Анализ следует фактическому телу registration и не заходит в отброшенные closures. Soundness это ухудшить не может.
- **A1–A3R.** Новых расхождений с выводами R2 не найдено.

Не закрыто целевыми прогонами:

| Случай | Что известно |
|---|---|
| Легальный PFC с shadow transfer внутри extent | Положительного результата нет ни на одной ревизии. Единственный прогон, дошедший до вердикта, — первый memprobe до S3: false FAIL при ≈ 14,4 GiB. Унаследованные upstream-тесты PFC + uninit by-value shadow не содержат |
| Replace, stub_verified, RecursiveCheck | Ноль тестов |
| M3: stack + promoted + alias + offset + overwrite + reset + false + Move в одном harness | Не выполнена на финальном export |
| Multi-harness в обоих порядках | Не выполнено на финальном export |
| `(*ptr).field = v` | Setter ставится только когда Deref — последняя проекция ([код][k-visitor-assign]); так же и в upstream. Теста нет; ожидается ложный FAIL при последующем чтении |
| Константный by-value аргумент обычного union | `operand_ty` доходит до `unreachable!()`; материализация константы сделана только для MU ([ветвь][k-const-store] · [ICE][k-operand-ty]). Унаследовано от upstream; пункт R2 открыт |
| Immutable origins вне допуска M1: под-срез с ненулевым offset, allocation с relocations, именованный static как операнд `raw_eq` | Ожидается fail-closed; контролей, фиксирующих это, нет |
| Projected in-place Move, повторная инициализация moved-from | Только формы из `maybe-uninit-call-move` |
| By-value DST со слотами MU | `transfers_shadow` признаёт slice, а сборка операции требует размер. Нужен явный отказ |
| B3 (ZST union), B4 (realloc, foreign) | Вне Part 1; нужны явные формулировки границы |

Тяжёлые fixtures возвращать в дерево с `-Z unstable-options --cbmc-args --object-bits N` и комментарием-ссылкой, как это сделано в `history/stub.rs`. Это не scope cut и не смягчение golden. N выбирать наименьшим, при котором хватает объектов.

Expected negatives. Golden подстрокой и общий `VERIFICATION:- FAILED` не исключают посторонних отказов. Для каждого negative нужен пер-харнесный список свойств с критерием «ровно N FAILURE с данным описанием и местом, остальные SUCCESS либо UNREACHABLE». Достигается script-based проверкой либо одиночным запуском harness. Тест, прошедший за счёт Unsupported или frameFAIL на более раннем шаге, не засчитывается.

Отдельно отмечу: frame-negative сейчас подтверждает только то, что нарушение ловится. То, что *законные* приватные записи при transfer frame проходят, видно в сводке D1 на уровне symex (`__check_lhs_assignment == TRUE`), но не подтверждено ни одним завершённым verification-прогоном.

### 13. Порядок шагов с нуля

1. **Прекратить:** реализацию G-SC, новые carriers (R9 и далее), converter profile C, поячеечные assigns.
2. **Шаг 0 из §2.6** (два пересчёта без запусков), затем **пакет шага 1** и исправление диагностического workflow: хвост журнала, артефакты, raw KiB.
3. **При подтверждении Г1:** вернуть два тяжёлых fixtures со сниженными object bits и исполнить R7-C `lawful-modifies`. Это первое легальное PFC-свидетельство. В плане зафиксировать переклассификацию блокера.
4. **Зависимости выпуска:** M3; решение по Replace и Recursive; контроли семантических краёв; ошибка вместо `unwrap_or_default()`; полный gate; исключение `docs/dev/*handoff*` и CI-overlays из экспорта.
5. **SmallSort:** G-SC-C продолжать как read-only инвентарь. Пункт «влияние кандидатных границ» заменить ресурсными признаками корня: PFC или нет, object bits профиля, проверяемые записи и локальные со взятым адресом внутри extent, циклы. Затем replay.
6. **Upstream, отдельными треками:** B1 как самостоятельный bugfix; анализ в kani#3611; мелкие замечания из ответа 11; пакет Part 1, разбитый на reviewable части.
7. **При опровержении Г1:** шаг 2 из ответа 5. Scope cut не выбирать, пока причина не названа.

Решения владельца:

- разрешить пакет шага 1 (порядка десяти коротких одиночных прогонов);
- принять политику «PFC + uninit тесты идут при сниженных object bits по upstream-прецеденту»;
- входят ли Replace и RecursiveCheck в заявление Part 1;
- открывать ли CBMC-трек (нужна lane со сборкой CBMC) и Kani-вариант 2 из ответа 6 (нужен trust review).
