На tmux 15 поставил бы две дифференциальные native-сборки. CMP1 в tmux 14 может продолжать реализацию для plain-пути U8/U9. Перестройку buffer пока отложить до сравнения.

1. Название «наблюдаемое ограничение проверенного v2 на двух PFC fixtures» уже соответствует U3B. Для утверждения «существующее ограничение upstream Kani» нужно сравнение с чистым production f046. Результат clean/U1/v2 классифицировать по фактическим SUCCESS, свойствам, Unsupported и Kani-reported OOM.

2. Сравнение проводить с побайтно одинаковыми repro/flags/runner и теми же exact roots. Clean-варианту нужен test-only patch, U1-варианту — неизменный production U1 плюс те же тесты. Зафиксировать production hashes, fixture hashes и каждый applied tree. Не сравнивать одновременно изменённый тест и модель.

- В оба пакета добавить маленький MU-free PFC с тем же `modifies(out)`, например простую запись u16 через out, и plain контроль. Он проверит доступный для всех баз путь без union blocker. Это поможет отличить общий PFC/uninit расход от конкретного transfer через buffer.
- Если clean даст Unsupported, а U1 — assigns, сравнение не установит регрессию v2: старые варианты ещё не проходили сопоставимый путь. Если U1 проходит тот же root, а v2 получает OOM, это установит ухудшение v2 на этом fixture. Причина «buffer внутри MEM_INIT_STATE» потребует отдельного изменения одной переменной.
- Два старых варианта с OOM покажут существовавшую проблему на этих repro. Только v2 OOM при непроходящих старых вариантах оставит причинность открытой. Off-negative SUCCESS сохранить как диагностический контроль без correctness credit.

3. Для buffer есть конкретная гипотеза. `codegen/contract.rs` добавляет весь static с marker KaniMemoryInitializationState в assigns DFCC. В v2 этот static стал содержать и transient argument/return metadata. Изменился разрешённый объект состояния, но рост encoding из исходника не следует.

- Отдельный static с собственным узким marker — допустимый кандидат следующего опыта после локализации. Это снова добавит целый static в assigns, поэтому ускорение заранее неизвестно. Альтернативы — более узкая область assign или специальная модель transfer при поддержке backend.
- Проверять такой вариант на той же v2 семантике, меняя только расположение/описание ghost state. Сохранить positive transfer, nested/two-argument/return, uninit negatives и пользовательский frame-negative. Добавить запрещённую запись в посторонний немаркированный static. Общее ослабление modifies или проверок контрактов не подходит.

4. Ближайший plain-путь CMP1 → U8/U9 этот OOM не блокирует. В CMP1-пакете до dispatch заменить известный непроходящий PFC-positive принятыми plain buffer controls и уже рабочим clause-PFC control. Пользовательский frame-negative сохранить. Проблемную PFC пару явно перечислить как отдельное открытое ограничение.

- Координатор может принять immutable v2 как экспериментальную базу для этого ограниченного профиля. Это решение не закрывает U3/PFC acceptance. После native compound PASS и review выполнять целевой U8/U9 replay с калибровкой.
- Не тратить отдельный общий replay на известные compound/select Unsupported. Для U8/U9 дождаться CMP1, для U7 — selected-storage transfer и решения по нужной PFC-интеграции.

5. Две сравнительные сборки разумно дать одним исследовательским этапом с cap $0.95, максимум две попытки по разным production-базам. При native work budget 5 мин резерв каждой $0.4725, вместе $0.945. Фактические ~$0.12 из прошлых запусков не заменяют резерв.

- Остаток ночи по брифу $5.3065. После cap $0.95 остаётся $4.3565 до прочих активных резервов. CMP1/core резервы сохранить при проверке общего ledger. Highmem для этой локализации сейчас не нужен.
- Если сравнение окажется несопоставимым из-за ранних отказов, следующий опыт выбирать по MU-free контролю и уменьшенному repro, с отдельным расчётом. Не переходить сразу к гипотезе второго marker или серии повторов OOM.

Для upstream v2 оставить подготовленным кандидатом части 1 с exact subset и PFC-ограничением. Два OOM не являются контрпримером soundness. Результаты сравнения определят, описываем ли существовавшее ограничение или исправляем ухудшение нашего патча перед ready-for-review.
