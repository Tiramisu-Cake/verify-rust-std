# Static assessment of contract-frame cost

The historical P1G observation reports 120.548 s for the complete selector. It does not split compiler, contract instrumentation, symbolic execution or SAT time. No new timing or execution was performed here, so a measured bottleneck is UNKNOWN.

The fixture itself has no loops and uses two small constant u16 inputs. `proof_for_contract(frame_target)` plus `modifies(out)` exercises DFCC frame instrumentation; the expected failure is the write through `outside` at main.rs:22. The two `inline(never)` callees retain nested two-argument and return transfers. `store_argument` nondeterministically selects an argument, and `load_argument`/`copy_by_id` branch on saved object IDs, offsets and tracked bytes. DFCC instrumentation together with these shadow-state paths is a plausible source of symbolic/backend work, not an established attribution of the 120 seconds. See library/kani_core/src/mem_init.rs:130,404,431 and kani-driver/src/call_goto_instrument.rs:185.

No source reduction is statically demonstrated to preserve all of this combined coverage.
