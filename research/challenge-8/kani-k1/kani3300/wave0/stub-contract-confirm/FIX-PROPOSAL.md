# Minimal clear-error candidate and support alternative

`fix-clear-error.patch` is isolated packet data. It has not been applied to either stock compiler or confirmation control. It applies cleanly to exact main by `git apply --check`; compilation, formatting and regression execution are NOT_RUN.

The candidate adds a guard in `kani-compiler/src/kani_middle/codegen_units.rs::validate_units` at line 319. For each ordinary-map source whose `KaniAttributes::has_contract()` is true, it reports at the harness span:

> ordinary stubbing of contracted function `<function>` is unsupported; use `kani::stub_verified` to use its contract

Validation already calls `abort_if_errors` before transformation. The guard neither returns an unconstrained success nor removes any contract body. It also rejects a PFC harness that tries to ordinarily replace the very function it claims to prove. The documentation change declares this exact restriction. `tests/ui/ordinary-stub-contract/main.rs` uses the same small `f/g` distinction, and its `expected` requires the new user diagnostic. The upstream UI regression should fail on main because the expected diagnostic is absent and pass on the candidate because it is emitted. Both expectations are source-derived and **NOT_RUN**; fixed-pass means acceptance by the error-output test, not a successful ordinary-stub proof.

Unchanged paths: `stub_verified` and PFC dispatch, verified-stub provider existence validation, assertions on unstubbed contracted calls, recursive contract modes and ordinary stubs of uncontracted originals. Their algorithms are untouched. Future regression selection must retain `tests/expected/function-contract/as-assertions/precedence.rs`, `simple_replace_pass.rs`, `gcd_rec_simple_pass.rs`, `tests/kani/FunctionContracts/stub_verified_safe_arbitrary.rs` and `tests/kani/Stubbing/stub_generic_param_rename_simple.rs`, plus standard upstream workflows for a future tool PR. This confirmation package runs no candidate or full matrix.

A support implementation is a separate alternative, not a hidden fallback: the transformation pipeline would track the selected body's definition alongside the original call identity and apply contract processing to that selected definition. An uncontracted replacement would have no contract instrumentation; a contracted replacement would use its own closure names. The design must explicitly reject or define overlaps where an ordinary map also replaces a PFC or verified target; silently bypassing PFC/verified processing would be unsound. It must define transitive stubs, replacement contracts, recursive calls, ordinary-to-verified overlap and replacement closure/helper identities. A narrowly scoped implementation could first support contracted originals with uncontracted replacements in ordinary proof harnesses and diagnose the remaining overlaps before transformation. That is broader than the submitted clear-error guard and needs its own tests and review.

Skipping `find_closure` when lookup fails is rejected: it hides arbitrary contract metadata defects and can discard required proof instrumentation. Reordering passes without selected-body identity is also insufficient: it can overwrite contract processing with an ordinary body or apply the original contract to a different body without an agreed policy.
