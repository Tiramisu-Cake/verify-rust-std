## Support versus a clear user error

Two coherent policies remain available. Full ordinary substitution would treat the supplied body as the verification assumption and supersede the original target's contract instrumentation; the MRE would then verify `f(x)==x+2`. Retaining original postconditions would instead reject that replacement by an ordinary assertion failure, and would be a materially different policy. Existing documentation does not resolve this distinction.

The minimal candidate here is an explicit unsupported-combination diagnostic before any body transformation, with a matching documentation restriction. It is a design recommendation, **not** a finding that stock main deliberately rejects the combination. It preserves proof checks and makes the unsupported case explainable. It should be chosen or replaced after independent review and native confirmation. The separate support alternative is specified in `FIX-PROPOSAL.md`; no compiler rewrite or missing-closure suppression is embedded in the stock confirmation.
