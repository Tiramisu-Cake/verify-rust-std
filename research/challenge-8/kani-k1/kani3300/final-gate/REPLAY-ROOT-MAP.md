## Sort4 matched negative: feasibility finding

The production body has a concrete live raw read path at `sort4_stable` (`smallsort.rs`, line 751): its first comparisons dereference source positions 1, 0, 3, 2, and later callback-dependent selected positions; destination is written only after comparisons. Therefore a hole at source slot 1 is a useful intended first-read candidate. Existing legal root has identical `[u64;4]` source/destination geometry and does reach that body.

However the same production helper carries `#[safety::requires(can_dereference(slice_from_raw_parts(v_base,4)) && can_write(dst[0..4]) && disjoint)]`. A one-hole MU source fails that precondition before the body read. Constructing `&[u64]` or calling `assume_init` first would itself read/claim the invalid value and contaminate the oracle. Consequently this is a GAP only for PFC/Assert mode: that mode's requires check rejects the hole before the body. Under the ordinary organizer profile, --no-assert-contracts selects the helper's Original body and omits the generated requires assertion; the test-only ordinary proof candidate in REPLAY-CONTROL-MAP can therefore call the actual helper and reach the raw read without an earlier slice/reference. This is a plausible source-level route, NOT_RUN until the exact Kani selector confirms the intended diagnostic.

The prepared test-only overlay and exact organizer argv are in REPLAY-CONTROL-MAP. It calls the actual helper from a test-only ordinary proof root under --no-assert-contracts; no slice/reference/assume_init is formed before the call. This is intentionally outside helper-contract proof credit and remains NOT_RUN.
