## 3. Что B3 меняет по коду

- `codegen_union` кладёт в `unionfield` логический тип arm и отдельно тип обёртки `{payload, padding}`.
  B3 меняет только `payload` обёртки и только при `layout-размер arm == 0`.
- `Expr::member` и `Expr::union_expr` берут логический тип; в irep тип выражения — логический, тип
  компонента union — обёртка. Обёртку видит только CBMC, когда обходит компоненты типа.
- Для `()` замена тождественна: `ensure_struct("Unit")` возвращает тот же `StructTag("Unit")`, новых
  символов и новых интернированных строк нет. Таблица символов — `BTreeMap` по индексу интернирования,
  так что порядок вывода тоже не меняется.
- Для arm нулевого размера другого типа меняется символ `tag-<union>::<arm>`: первый компонент `T` → `Unit`.
  Оба имеют ширину 0. Литералов, шагов SSA и ширин это не добавляет.
- Статический census. `MaybeUninit` не меняется. В std nightly-2026-10-23 меняются: `Data<F, R>` в
  `std::panicking::catch_unwind` при ZST-замыкании или `R` нулевого размера (`panicking.rs:499`),
  `Data<T, F>` в `LazyLock` при ZST `F` (`lazy_lock.rs:14`), `Transmute` в `transmute_prefix` и
  `TransmuteFrom::transmute` при одной ZST-стороне. В s2n-codec, s2n-quic-core, s2n-quic-platform,
  библиотеках Kani и остальных perf-тестах своих union нет. bolero под `cfg(kani)` подключает
  `noop/panic.rs` и `catch_unwind` не вызывает — по HEAD репозитория bolero, опубликованные версии не
  сверял. Сторонние зависимости на union не просмотрены.
- Память пика. `sync::spsc::tests::alloc_test` помечен `kani::solver(kissat)`: одновременно живут CBMC
  и внешний kissat. По цифрам первой редакции запроса (не сверены) top-процесс занимал 6.9 ГБ при
  1.8 ГБ доступных в s2n и 10.6 ГБ при 4.4 ГБ в `display_trait`. Сумма «top + доступно» в s2n на
  6.3 ГБ меньше, чем в `display_trait`: эту память занимает не top-процесс. Монитор одного
  top-процесса пик не измеряет.
- Старая база — не контроль для v4. #5115 убрал чтение старого значения в atomic store с unit-результатом;
  `spsc` построен на атомиках, поэтому GOTO `alloc_test` между базами различается и у main, и у v4.

## 4. Ответы на вопросы

**1.** Допустимо: «на базе `0aac16ef62` штатный perf-job в форке 14–15.11 перемежающе теряет раннер —
с B3 в 3 запусках из 3, без B3 в 3 из 14; причина потерь и связь с B3 не установлены». Недопустимо:
«B3 вызывает OOM или регрессию», «main стабилен, v4 нет», «B3 не влияет — доказано». Три потери v4 — не
три независимых измерения: две попали в окно, где без B3 терялось 3 из 5. Минимальное различающее
свидетельство — T1: при идентичном входе CBMC эффект компилятора на solver невозможен, остаётся среда.
Статистикой этого не решить: при фоновой доле потерь 20–35 % одна пара на разных VM почти ничего
не различает.

**2.** Как первичный шаг D1 не годится: он тяжёл, оба плеча упираются в потолок 16 ГБ, а одна пара на
разных VM гипотезы не различает. Заменить на T1, D1 оставить условным (§5). Убрать из D1 полный
perf-набор, фазовые счётчики и раздельные VM. Чтобы сохранить данные и не создать новый оракул:

- лимит задаёт ядро, а не опрос: нагрузка в cgroup v2 с `memory.max` ниже RAM (резерв раннеру 2–3 ГБ)
  и `memory.swap.max=0`. Превышение даёт `oom_kill` в `memory.events` и статус 137, который kani-driver
  сам печатает как out-of-memory; раннер жив и выгружает артефакты. На hosted-раннере я это не опробовал:
  сначала минутный пробный job;
- пик — `memory.peak` cgroup (точный, всё дерево процессов) и `ru_maxrss` каждого `cbmc` и `kissat`
  через PATH-обёртки с `/usr/bin/time`; опрос MemAvailable — только фон;
- exit каждого вызова писать в журнал; без `|| true` и без `grep` в конвейере без `PIPESTATUS`;
- срабатывание лимита — INCOMPLETE(cap) для сравнения, не PASS и не FAIL;
- оба плеча на одной VM последовательно (A, B, A), иначе неоднородность пула смешается с эффектом;
- в начале job записать `MemTotal`, swap, `nproc`, модель CPU, версию образа, `df`;
- kill — группой процессов: сторож, убивающий только `cbmc`, оставляет внешний `kissat` сиротой.

**3.** Отдельный census не нужен: diff таблиц символов в T1 им и является. Статическая оценка — в §3;
для s2n-quic-core изменённых форм не ожидаю.

**4.** По убыванию ценности: (1) sha256 `*.symtab.out` и `*.out` — при равенстве всё ниже по конвейеру
одинаково; (2) при неравенстве diff `goto-instrument --show-symbol-table`, затем функций; (3) для одного
offender sha256 DIMACS (`cbmc … --dimacs --outfile`), равенство означает одну и ту же задачу для kissat;
(4) версии и sha256 бинарников `cbmc`/`kissat`, фактический argv из `--verbose`. Seeds, порядок clauses,
allocation profile и статистика byte-extract не нужны, пока (1) не показал различий. Разные checkout paths
не допускать: оба компилятора собирать на одном абсолютном пути, с одним target-dir и одним `Cargo.lock`;
тогда нормализация не требуется. Если она понадобится, её проверяют A/A (ноль различий) и положительный
контроль: компилятор старой базы обязан отличаться на harness с atomic store.

**5.** При одинаковом выходе компилятора не может отличаться ни одна фаза. Где форма меняется, оба типа
имеют ширину 0: меняется лишь дерево выражения при понижении byte-операций над таким union. Про
параллельную память — §3; процесс локализуют `ru_maxrss` по обёрткам, сумму — `memory.peak`.

**6.** Факториал и бисекция сейчас не оправданы. Условие запуска: на одной VM не менее трёх раз
различается детерминированная метрика одного harness — хэш GOTO/DIMACS или `memory.peak` сверх A/A-шума.
Достижимость 13 коммитов в default perf-профиле: GOTO меняет #5115 (`intrinsic.rs`); достижим, но
нейтрален для niche ≤ u64::MAX — #5066; #5152 трогает `kani_middle` на общем пути, по описанию без
явных tail calls вывод не меняет, кода не читал; не на пути perf-harness — #5058 (в s2n-крейтах нет
`kani::block_on`/`spawn`), #5153, #5134, #5093, #5063, #5092, #5057 и uninit-часть #5115 (за `-Z`),
