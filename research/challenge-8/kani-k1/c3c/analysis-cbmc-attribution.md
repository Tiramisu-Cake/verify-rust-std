# CBMC process to harness attribution

## Source-verified behavior at the pinned Kani revision

At Kani `9461e07af7ec929f050aa4192f29363c9be07779`, the regular/manual proof path records both the user-facing `pretty_name` and compiler `mangled_name` in `HarnessMetadata`. The manual proof model stem is formed as `<base-file-stem>_<mangled_name>` (`kani-compiler/src/kani_middle/metadata.rs`, `gen_proof_metadata`). The driver obtains the harness Goto artifact, then `run_cbmc(file, harness)` invokes `cbmc`; `cbmc_flags` appends `file` after custom arguments, then adds `--verbosity 9`; `run_cbmc` adds `--json-ui` for terse/regular output. The model is not the final argv token. The pinned `cbmc_flags` body does not add a `--function` selector (`kani-driver/src/call_cbmc.rs`). Thus the usable ordinary-harness identity in a live CBMC argv is the positional model path, provided the exact `mangled_name -> pretty_name` metadata mapping is available.

Do not infer a printed harness from the Rust v0 symbol's leaf text or from a family substring. Rust v0 identifiers are length-encoded, but the symbol grammar also includes nested paths, generic-argument paths, backreferences, disambiguators, optional suffixes, and implementation-defined details. A decoded leaf alone does not establish the containing family or the instantiated pretty name. Without a demangler or an exact compiler metadata mapping, family/name attribution from a raw mangled path is not established.

Autoharness needs separate handling. Its model filename contains a SHA-1 digest of the target mangled name followed by `_autoharness`; compiler metadata's `mangled_name` is the generated harness name, while `pretty_name` describes the target (`gen_automatic_proof_metadata`). This hashed filename cannot be reversed into the displayed harness. The function-selector comment in that metadata generator is not evidence that a `--function` argument appears in ordinary CBMC argv; the pinned generic `cbmc_flags` implementation shown above does not add one. Attribute autoharness only if a captured selector exactly maps through metadata or another pinned, source-bound identity record.

## Attribution rule and helper

`analysis-attribution.py` takes argv tokens and an externally collected exact mapping from Kani metadata `mangled_name` to `pretty_name`. It returns `direct` only when exactly one complete known v0 identity is found in the manual model basename (or in a recognized `--function` option) and the identities do not conflict. Unknown symbols, hash-only autoharness names, partial matches, and ambiguous selectors stay unresolved. It never demangles or guesses from a concurrent harness set. The built-in fixtures cover exact path/selector matches, partial mismatch, hash-only autoharness, and multiple recognized selectors.

The built-in fixtures are synthetic parser fixtures; they do not establish that a real summary page contains full CBMC argv or a matching metadata map. A safe future sampler must retain the complete NUL-delimited argv/model path and the build/source identity, and the same build must provide the exact harness metadata map. If only a shortened command hint and simultaneous `Checking harness` set are present, keep the peak as `active-set-ambiguous`; do not rewrite historical C3b rows as per-harness peaks.

## What the historical evidence can establish

The C3b peak tables retain only a short command hint, e.g. `cbmc_--no-malloc-may-fail_--no-undefined-shift-check_--no-si`; this excludes the later model-path token. The current sampler's direct regex searches for the readable Rust path inside the CBMC command line, while Kani supplies a mangled model filename as the positional model argument. Therefore the direct match is not supported by the observed command shape. Existing peak records can still support aggregate and active-set accounting, but cannot be retroactively assigned to one harness using the truncated hints.

## Same-build metadata file and exact path join

The compiler writes one JSON metadata file per crate at `tcx.output_filenames(()).path(OutputType::Object).with_extension("kani-metadata.json")`. In Rust path terms this is the same parent directory and object-file stem as the compiler output, with the two-part extension replaced by `kani-metadata.json` (`kani-compiler/src/kani_middle/codegen_units.rs::metadata_output_path`; `ArtifactType::Metadata` is `kani-metadata.json` in `kani_metadata/src/artifact.rs`). The exact output directory is therefore the per-crate rustc output directory; do not hard-code a guessed `target/{profile}/deps` path. During `kani verify --std`, Kani creates `<target-dir>/kani_verify_std`, runs `cargo build -Z build-std=panic_abort,core,std` from that project, collects the compiler-emitted metadata paths, deserializes them, and constructs `Project` before harness execution (`kani-driver/src/project.rs::std_project`; `kani-driver/src/call_cargo.rs::cargo_build_std`).

JSON schema is serde's field-name schema (snake_case; no rename attributes on these structs): top level includes `crate_name`, `proof_harnesses`, `unsupported_features`, `test_harnesses`, `contracted_functions`, and `autoharness_md`. Each `proof_harnesses[]` object has `pretty_name`, `mangled_name`, `crate_name`, `original_file`, line fields, `goto_file`, `attributes`, `contract`, and flags. The `attributes.kind` enum distinguishes `Proof` and `ProofForContract: { target_fn: ... }`; contract proof harnesses are members of `proof_harnesses`, not a separate `contract_harnesses` array. `test_harnesses` is separate. (Sources: `kani_metadata/src/lib.rs::KaniMetadata`, `kani_metadata/src/harness.rs::HarnessMetadata/HarnessAttributes/HarnessKind`.)

For a direct, source-bound runtime join, the worker can cache the JSON files in the CBMC model's parent directory once per build, index every `proof_harnesses` (and `test_harnesses` if relevant) entry by its `goto_file`, then replace the `.symtab.out` extension with `.out` and compare the resulting canonical path to the positional CBMC model path. This uses the metadata's own `goto_file`, so it uniquely covers ordinary and hashed autoharness models without parsing Rust v0 or guessing a filename prefix. The transform is Kani's `convert_type(SymTabGoto, Goto)`; `Project::get_harness_artifact` canonicalizes that expected path and matches it to the artifact; the harness runner passes that artifact path into `run_cbmc`. Keep a match only if exactly one metadata row joins to the canonical model path; missing/duplicate rows remain unresolved. Capture `pretty_name`, `mangled_name`, metadata-file path, and build/source identity in the sample record.

Correction/scope of the earlier helper: `analysis-attribution.py` demonstrates a conservative symbol-map fallback, and intentionally leaves hash-only autoharness paths unresolved. The same-build `goto_file` join above is stronger and also resolves those autoharnesses; the helper has not been extended to read metadata JSON.

## Final resolver contract after call-site review

The complete live argv ends with verbosity/JSON flags, so production resolution scans `.out` candidates and requires exactly one positive compiler-metadata path match. Relative `goto_file` paths follow the driver process cwd, not the metadata directory; the cache key includes cwd. Null `goto_file` entries have no model identity and can be skipped. The raw metadata serde arrays are present even when empty. The production observer is in `tools/kani_k1.py`; `analysis-attribution.py` remains an earlier synthetic symbol-map fixture helper, not the observer used for new builds.
