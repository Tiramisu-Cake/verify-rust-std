## Работа и обязательные gates

### Gate 0 — применимость метода

1. На точной выбранной базе `S_M`/`S_M′` зафиксировать фактические requires/call-site геометрию actual `bidirectional_merge`; проверить совместимость Kani `proof_for_contract`/`stub_verified` с u8/u64, sorted-only ensures и R11 precondition control.
2. Проверить, принимает ли Kani `9461e07a` контракты на `#[inline(always)]` `merge_up`/`merge_down`: `mut`-параметры, generic `T` в `old()` и возвращаемый кортеж указателей. При assert-contracts новые `requires` начнут проверяться также в существующих гармониках; сверить фактические флаги lane (включая `--no-assert-contracts`) и влияние на прежние callers. Это отдельный capability gate, поддержку заранее не считать установленной.
3. До дорогого прогона показать, что proposed observations привязаны к actual body, а не к копии алгоритма или независимой целочисленной модели. Не вводить новый trusted model/toolchain без отдельного решения.
4. Если для этого необходим runtime-код, непроверенное предположение о записи/курсорной идентичности или несогласованный контракт, остановиться: записать конкретный blocker и варианты дизайна. Не продолжать к gate (б) в расчёте на его замену structural gate.

При контрактах на одиночные pointer-helper’ы не подменять геометрию проверкой одного адреса. `can_dereference`/`can_write` на текущем слоте покрывает чтение/запись только этого слота; для `add`/`sub` ещё нужны same-allocation и корректные in-bounds/one-past границы получаемого указателя. У `merge_up` оба source и `dst` продвигаются через `add`, поэтому требуется соответствующая область курсоров и допустимость следующего one-past указателя. У `merge_down` `dst.sub(1)` после записи требует, чтобы predecessor оставался в той же allocation (для non-ZST); source `wrapping_sub` может формировать курсор за границей после исчерпания, но такой курсор нельзя разыменовывать. Два source-курсора — shared reads: они могут совпасть, отдельное source-source disjoint требование не нужно; `dst` обязан не перекрываться с источником, переданным `copy_nonoverlapping`. Сигнатуры helpers не несут base/len, поэтому полноценную геометрию их предусловием в общем случае не выразить без caller context. Допустимо расширять requires только условиями, истинными для всех actual call sites; сначала перечислить их и доказать, что contract не отсекает реальный caller. Иначе оставить memory-safety bounds у caller wrapper с длинами/регионами, а local helper contract ограничить доказуемой one-step семантикой.

### X6а — структурная перестановка actual merge и controls

1. Наблюдать реальные шаги `merge_up`/`merge_down`: ровно один соответствующий source-cursor перемещён на единицу в правильную сторону, другой сохраняется; адресная геометрия сопоставлена исходным регионам с корректным provenance. Проверить odd tail и начальные/финальные границы.
2. Для `dst` показать, что front/back/odd-tail записи не пересекаются и вместе покрывают ровно `0..len`, каждая ячейка записана один раз и снаружи региона записи нет.
3. Связать каждую фактическую copy-операцию с текущим выбранным source-cursor и значением; одного подсчёта записей и равенства конечных счётчиков недостаточно. Зафиксировать, что других записей нет, а source остаётся неизменным при чистом comparator и disjoint `dst`.
4. Точная финальная проверка actual body: normal return только при `left == left_rev.wrapping_add(1)` и `right == right_rev.wrapping_add(1)` после возможного odd-tail шага.
5. Два controls должны различать исходник и мутанты с source-map: (i) повторная запись ячейки `dst` — ожидаемый FAILED по однократности/покрытию; (ii) удаление финальной проверки — ожидаемый FAILED по однократному потреблению/permutation с несогласованным comparator. Если выбранные утверждения не различают требуемый мутант, gate не пройден. Для чистого строгого слабого порядка FAILED на удалении guard не обязателен, если guard там семантически избыточен; structural gate всё равно должен быть различающим на предусмотренном control-домене.
6. Домены отдельно: нормальная функциональная претензия — чистый strict weak order и normal return, вариант (А) исключает только `panic_on_ord_violation`, unwind не заявлять. Structural sensitivity — ordinary proof реального тела без stub самого bm, в штатном `--no-assert-contracts`, с произвольным read-only comparator CD-2: original сохраняет реальный guard, есть cover normal return и достижимости guard; после удаления guard эквивалентный `assume` в harness запрещён.
7. Плановый размер: 4 positive + 2 negative entries: малые u8/u64 odd/even witnesses len2..3, затем полные семейства len2..32 и два mutant entries на u64. Обязательные boundary covers: 2, 3, 16, 17, 20, 24, 31, 32 и финальный guard. Если split увеличивает entries, пересчитать стоимость до dispatch; недостающие controls нельзя удалить ради cap.

**STOP X6а:** если actual-body observation/source binding недостижим без изменения runtime, копии тела или невалидированной модели, немедленно остановить весь X6 и запросить design решение через RESULT координатору. PASS позитивной harmony без обоих controls не даёт GO.

### X6б — sorted-only contract и темп

Только после GO gate 0 и X6а проверить `proof_for_contract` actual `bidirectional_merge`, sortedness only, отдельно для u64/u8: N16 → N20 → N24. До двух N32 (по типу) разрешены только по измерительному gate. Включить два R11 negative entries — по одному на тип, с достижимым нарушением requires при `stub_verified`; это отдельные controls от structural mutants. Сначала подтвердить, что callee preconditions применимы. Новые/изменённые ensures допускаются только в изолированном экспериментальном профиле с ledger; зависимые callers перед переносом проверяются повторно.

Для каждого типа отдельно записать успешные Verification Time `t16,t20,t24`; whole-job wall — отдельно для бюджета. `g16_20=t20/t16`, `g20_24=t24/t20`, `g=max(1, доступные успешные g)`. Плановый прогноз: `P32=t20*g^3` или после N24 `P32=t24*g^2`. TIMEOUT — только нижняя граница, не значение времени/темпа.

- **GO к пробе N32:** X6а пройден и `P32 ≤ 600с`, плюс проверены бюджет и memory/slot ограничения. Зачёт N32 — только при прямом SUCCESS ≤600с.
- **GO к ограниченной следующей порции до24:** прямой N24 SUCCESS ≤600с даже при плохом P32; это не обещает порог32. Если после N20 прогноз плох, допустим один заранее учтённый N24 в пределах cap.
- Если нет ни одного основания GO — STOP для типа/направления, с результатами, временем и измеренным ростом. Быстрый sorted-only PASS без X6а не даёт GO на полную корректность.
- GO нужен обоим типам либо для u8 отдельно с явной редукцией порядка: ≤32 значений дают ≤32 классов строгого слабого порядка, u8 позволяет ранги с равенствами. Редукция применима лишь после проверки, что управление actual body зависит только от этих сравнений, а остальные операции переносят значения. Она не переносит память/UB, эффекты comparator, геометрию, ветви типа и стоимость u8 на u64. u8-доказательство не даёт `stub_verified` кредит u64.
- Итог N16/20/24 — 6 positive entries; до 2 N32 только по gate. После STOP следующие entries — NOT_RUN. С X6а и R11 ожидаемый полный пакет — 10 positive +4 negative, условно до12 positive +4 negative.

### X6в — композиционный довод

Составить таблицу `шаг → входной логический регион → выходной регион → свойство → source/type/length/region evidence` для подготовки/копии scratch, sort4/sort8, insert_tail, сетей, actual merge и копии результата. Копирование создаёт физическую копию: мультимножество всей памяти вместе со scratch не является инвариантом. Доказать сохранение последовательности/мультимножества между названными логическими регионами на каждом шаге с frame, no-alias и точным выбором следующего региона. Для каждого callee перестановка должна иметь собственное основание; sortedness её не заменяет.

`stub_verified` caller может использовать только действительно доказанные sorted-only ensures в совместимом типе, длине и регионе. Kani-перестановка caller при stub без доказанного permutation-ensures запрещена как claim; её обосновать отдельным композиционным доводом actual source. Не добавлять ручной assume permutation, не считать E3 закрытым sortedness и не трактовать композиционный довод как разрешение добавить недоказанное ensures. В отчёте раздельно маркировать Kani results и структурный довод.
