## Что сделать (порядок обязателен)

0. **Кандидат.** Влить коммит C3a ветки подачи `e9655515` (types.rs, smoke, `mod types;`). Исправить
   замечания `REVIEW-C3B.md`. Варианты C3b зависят друг от друга (D использует `proof_cover!` из E, R сам
   ставит kissat) — составить итоговый объединённый diff `library/` против `e9655515` и таблицу
   «старый домен → новые гармоники» для каждого изменённого семейства. Решить про K (kissat) по данным:
   оставить только там, где есть измеренная польза. Rustfmt-check (ниже) — exit 0.
1. **Новый kind лейна `autoharness`** (минимальное изменение `kani_k1.py`/`gcb-k1.sh`/`k1g.sh` + тесты в
   `test_kani_k1.py`): **дословно** команда шага `Run Kani Verification` job `kani_autoharness` из
   `.github/workflows/kani.yml` проверяемого SHA (все `--include/--exclude-pattern`, `--jobs=3`,
   `--harness-timeout 10m`, `--default-unwind 1000` и т. д. — брать из файла, не переписывать руками), на
   `gcb-e2-standard-4` (16 ГБ, 4 vCPU; свопа у GCB нет, у GH ubuntu ~3–4 ГБ — записать отличие).
   Обязательно: корректный exit-код через `tee`; полнота результатов (каждая начатая гармоника получает
   итог или помечается как отсутствующая); парсер по потокам `Thread N:` (jobs3, TIMEOUT без Verification
   Time, обрыв) с тестами на эти случаи; память — пики driver, cbmc, отдельного solver, одновременная
   RSS-сумма с отметкой времени, доступные cgroup/OOM-показатели (`memory.events`, `dmesg`, если читаемо).
   RSS не приравнивать к физической RAM. Резерв этого kind — по фактическому лимиту времени сборки,
   ставка $0,0135/мин. Полный лог по-прежнему не читать — только summary/peaks/log-grep/log-lines.
2. **Дешёвые различающие пробы (jobs3, kind `diagnostic`):** matched-пары «до (e9655515) / после
   (кандидат)» на одном наборе: три macOS TIMEOUT + самые тяжёлые по `mac-times.tsv` (≥ 400 с) +
   три гармоники, шедшие на ubuntu в момент остановки. Время и память по гармоникам.
   Плюс, если остаток бюджета позволяет после п. 3, — opt-in аудит перенесённых E covers на кандидате
   (`cfg kani_smallsort_controls`, выборка по семействам; все covers SATISFIED, кроме объяснённых); если не
   помещается — так и записать.
3. **Полный прогон kind `autoharness` на кандидате** — один. Baseline полного job на `e9655515` можно
   пропустить; тогда не заявлять ни воспроизведение причины сбоя ubuntu, ни измеренное улучшение полного
   job. Если кандидат проходит — вывод «на GCB 16 ГБ job прошла с пиком X», не «на GitHub пройдёт».
4. **Критерий времени.** Рабочая цель — каждая ordinary ≤ 300 с на macOS. Прогноз macOS — калибровка
   отношений mac/GCB **только на действительно неизменённых моделях** (callee, stubs, solver, unwind те же),
   по семействам, с размером выборки, хвостом и цензурированными случаями (TIMEOUT не выбрасывать).
   Прогноз — не приёмка: итоговая приёмка — новый П-6 (решение владельца).
5. **Лечение** гармоник с прогнозом > 300 с: разбиения без сужения домена (проверить объединение
   доменов и суммарную стоимость семейства — разбиение может уменьшить пик, но увеличить сумму и объём
   удерживаемых результатов). Не ограничиваться историческими 18: после D/R модели и число гармоник
   меняются — полный inventory (`kani list`) итогового SHA и реестр рисков по нему.
   **Перенос proof-гармоник в opt-in — не делать**; оставшиеся > 300 с — список в отчёт как опция
   владельцу с перечнем теряемых доменов и зависимых композиционных утверждений.
6. **Таблица CI-budget** для владельца: фактический wall job (GCB), сумма Verification Time наших и всех,
   доля SmallSort, пики памяти, failures/timeouts, источник каждого числа; сравнение с mac-times (П-6).
