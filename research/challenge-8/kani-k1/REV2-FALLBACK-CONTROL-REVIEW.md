## Блокирующие замечания

1. **Рабочий guard принимает другой tree с тем же parent.** `check_trigger` сравнивает tree с `expected_tree`, только когда аргумент передан. Оба вызова из `fallback_run.py main()` опускают аргумент, а `identity` получает tree, прочитанный из проверяемого `HEAD`. В отдельном временном checkout фактический entry point `fallback_run.py pins` вернул `0` для заявленного tree и для `d805a01c2af3eab20763d175c29f639a53e67792`, полученного добавлением одного файла к заявленному tree. В обоих случаях событие указывало на соответствующий SHA, ref и единственного parent. Отрицательные контроли с другим parent и attempt `2` вернули `1`. Тест с явным `expected_tree` проверяет ветку helper, которую workflow не вызывает. Нужен обязательный доверенный pin для исполнения либо внешняя обязательная проверка одобренного tree и parent до dispatch. Регрессия должна отклонять другой tree с корректными event SHA и parent через фактический путь допуска. 2. **Окно 600 с не включает гарантированное завершение записи receipt.** `measure_slot` вычисляет elapsed и проверяет `finished_by` до синхронного `save_receipt`. Сама атомарная запись не ограничена дедлайном, после неё проверка отсутствует. В синтетической проверке с валидным `RSS_LIMIT` и подтверждённым reap при дедлайне `1600.0` запись завершилась в `1600.1`. Сохранённый receipt показал `599.8` с и `RSS_LIMIT`, кампания осталась без признака превышения. Нужна ограниченная дедлайном финализация с измерением завершения записи и сохранением причины превышения при исчерпании окна. Ранее сохранённый технический receipt должен оставаться доступен при таком отказе. [Окно и запись](/root/kani-rev2-fallback-control-w11/ch8-cal1/fallback_run.py:220) · [Последняя проверка](/root/kani-rev2-fallback-control-w11/ch8-cal1/fallback_run.py:253) · [Атомарная запись](/root/kani-rev2-fallback-control-w11/ch8-cal1/run.py:24)

3. **Ранний отказ проверки замороженных входов оставляет все три слота без receipts.** `pins` вызывает `spec.load()`, который проверяет request и SHA-256 bundle. При отказе `pins` верхнеуровневый обработчик сохраняет `error.json` во временном каталоге, а `steps.pins.outcome == 'success'` блокирует `finish` и вслед за ним upload. Предусмотренный в `finish` путь с `request_error` и доверенным roster при таком отказе недостижим из workflow. После допуска trigger отказ проверки входов должен публиковать причину и три именных `NOT_STARTED`, без запуска setup или слотов.
