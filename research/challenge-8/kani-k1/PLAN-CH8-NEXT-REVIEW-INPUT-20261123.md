## C. Технические тезисы — проверить по исходнику и данным

1. Ось размера типа: в small_sort_general_with_scratch на N16–N32 два sort8_stable идут только при
   size_of::<T>() <= 16; для типов крупнее — два sort4_stable. Наше «N16–N32 = два sort8_stable»
   неполно. Нужна ось размера типа в калибровке.
2. macOS: 7,28–7,35 GiB = 7,8–7,9 GB при 7 GB у runner. Точку решения по macOS не ждать — не влезет.
   Плюс на macOS KANI_JOBS пуст, run-kani.sh передаёт `-j` без числа (несколько проверок сразу).
   Предложение: просить организаторов задать KANI_JOBS для macOS, а не особый профиль; запасной
   вариант (самые тяжёлые проверки только на Ubuntu) — только открыто с ревьюером. Объединять
   геометрии не стоит: растёт пик одной проверки. У задач нет timeout-minutes; партиция уже 85 мин.
3. Бюджет CI как входное условие плана: предел времени и памяти на одну проверку и допустимый
   прирост партиции. Ориентир организаторов ~2 мин; наш sort13 — 13–15 мин.
4. Вместо проверки на каждую длину — одна проверка с символьной длиной поверх контрактов insert_tail
   и bidirectional_merge. Для сети и unstable general перебор до 32 — уже полное доказательство (выше
   порога abort); обобщение на любые длины нужно только вставкам и stable general — loop contracts
   (-Z loop-contracts в CI включён, текст задания их упоминает).
5. Аргумент по типам: при чистом компараторе код видит только результаты сравнений; ранги 32
   элементов укладываются в u8, поэтому в пределах маршрута порядок на u8 переносится на другие
   ключи. Kani этого не проверяет — аргумент для ревьюера вместе с проверками памяти на каждой ширине.
6. Типы с нишей (bool, char, NonZero) в PR: у u8, u64 и байтовых массивов любой битовый шаблон
   допустим, проверка валидности на них пуста.
7. Object-bits 11 против 12 для сети: почему 11, пробовали ли 12. Без этого неясно, препятствие это
   или непроверенная настройка.
8. kani#5104 (Soundness): описание PR признаёт зависимость четырёх фикстур с массивами; в PR
   объяснить, почему выводы не слабеют.
9. Сопровождение: #784 (21.11) обновил subtree std до nightly-2026-11-19; после каждого такого
   обновления сверять время и память проверок.
