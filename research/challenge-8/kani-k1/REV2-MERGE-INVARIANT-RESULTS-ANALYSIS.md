## Что видно в GOTO и чего ещё не видно

1. **Инструментирование применилось.** У обоих слотов `loop-capture.json` связывает exact harness с аттестованным `goto-instrument`, argv `--dfcc --apply-loop-contracts --loop-contracts-no-unwind` и полными digests до и после. До DFCC у мономорфизации `bidirectional_merge::<u8, KeyLess<u8>>` один обычный latch `GOTO 26`, у guard сохранены `#spec_loop_invariant` и `#spec_assigns`. После DFCC у этого же `for` на строке 1044 есть loop `.0`, `ASSERT` базы и шага, проверка inclusion для `assigns`, восемь целей write set и `havoc`. Восемь целей — шесть курсоров, scratch через `object_upto` и добавленный индекс. Actual `merge_up` и `merge_down` сохранены в теле. Оба снимка post используют те же структуры, а контроль меняет предикат в отдельном Std overlay. Снимок показывает генерацию обязательств. Для факта их достижения, пригодности write set и безопасности нужен завершённый нативный результат. [Positive GOTO capture](/root/ch8-artifacts/run-45694112028/ch8-rev2-merge-invariant-Linux-X64-45694112028-1/slots/M32-NATIVE-INVARIANT/loop-capture.json) · [Control GOTO capture](/root/ch8-artifacts/run-45694112028/ch8-rev2-merge-invariant-Linux-X64-45694112028-1/slots/M32-STEP-CONTROL/loop-capture.json)
2. **Остаточный back-edge соответствует индукции.** В сохранённых секциях `post_dfcc.function_section` единственная обратная дуга на строке секции 847 — `if __in_base_case GOTO 20`. В цели на строке 577 флаг сбрасывается, затем идут база, write set, havoc и предположение инварианта. На следующем latch проверяется шаг, затем `ASSUME false` обрывает этот путь. Это конкретная первая пара и абстрактная пара либо выход, а не обычный проход всех 16 пар. `--loop-contracts-no-unwind` оставляет преобразованный цикл в таком виде. Общее unwind36 сохраняется для остаточных циклов. Снимок одной функции и незавершённый symex не дают итогов unwinding внутри её вспомогательных функций. [Параметры инструментария Kani](https://github.com/model-checking/kani/blob/9834c96ce90ff57d8495416530b080dc3d52ce25/kani-driver/src/call_goto_instrument.rs#L175-L209) · [Ревью модели цикла](REV2-MERGE-INVARIANT-REVIEW.md#поддержка-пина-и-условия-диагностики)
3. **Возможная цена перенесена в предикат и память.** После havoc шести raw pointers, индекса и scratch symex обрабатывает `pointer_object`/`pointer_offset`, проверки разрезов и повторные вызовы `scratch_matches`. Последний содержит обход 32 позиций с условием на символический k и типизированными raw reads заполненных краёв. Предикат вычисляется в нескольких контекстах базы, предположения и шага. Дополнительные остаточные циклы есть в `count_below` и проверках числового порядка половин. Возможна также стоимость DFCC memory checks при символических адресах. Идентичная стадия у контроля совместима с общей ценой этих вычислений до выдачи свойств. По captures нельзя ранжировать эти причины или объявить ошибку пина. Полный actual Mask Proof FIX3 доходил до CNF после 10,6 с symex. Новый путь сократил разворачивание основного цикла, но на данном предикате даже не дошёл до этапа, на котором остановился FIX3. ## Решение и оценка

- **Сейчас, 0 новых пакетов.** Сверки сохранённого GOTO достаточно, чтобы закрыть вопрос о применении контракта к actual loop. Ветку с текущим предикатом поставить на паузу. Увеличение окна для того же корня не определит, какая часть symex вызвала задержку. Повтор с большим RSS или другим OB не проверит причину при наблюдаемом пике CBMC 0,27 GiB. Для N13/N17 продолжать no-merge путь независимо от инварианта. Для N32 уже подготовлен внешний перенос левого S13, который нужно принять в графе отдельно. [Левый S13](REV2-S13-LEFT16-HANDOFF.md)
- **Предпочтительный путь для merge, оценка 1–2 инженерных дня без CI.** Привязать успешный `M32-PAIR-STEP` FIX3 к actual init, 16 вызовам пары и финальным курсорам через внешний индуктивный аргумент о рангах, с проверкой исходника и доменов как у S13. В доказательстве оставить точные destinations, frame, инициализацию обоих краёв scratch и переход к copy-back. Согласовать пригодность такого правила для допуска до подготовки consumer. При принятии — один следующий Ubuntu-пакет на сквозной N32 и различающий контроль, если выбранный способ композиции реализуем. Отдельный odd exit потребует своей проверки. Внешний вывод сам по себе не квалифицирует `stub_verified(bidirectional_merge)`. [Требования к N32](REV2-MERGE-INVARIANT-REVIEW.md#до-допуска-n32)
- **Если требуется именно native loop contract, оценка 1–2 инженерных дня и один диагностический Ubuntu-пакет.** Пробовать только управляемую дельту. Оставить тот же actual `for`, курсоры, write set, профиль и input, а в диагностическом варианте заменить `scratch_matches` на предикат только о курсорах и разрезах. Сохранять bounded нативные маркеры symex, `Unwinding loop` с ID и source location при наличии, последний progress и CPU process samples. При появлении CNF в дешёвом варианте будет подтверждено влияние проверки scratch. Тогда вернуть свойство через эквивалентную более компактную кодировку, например проверяемую композицию по одной независимой позиции. Если и лёгкий вариант останавливается до CNF, дальше изолировать DFCC havoc и адресные предикаты в отдельном минимальном воспроизводителе или отложить этот маршрут на данном пине. Диагностическое ослабление не даёт proof credit. Любой принимаемый вариант снова проверяет полный пост, frame, инициализацию и matched отрицательный контроль в пределах VT 120 с и 4 GiB.
