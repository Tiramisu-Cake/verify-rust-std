# Kani undefined-behavior detector controls

These isolated harnesses measure available Kani checks. They do not prove
SmallSort, and a negative control is expected to fail. Run each harness
separately so one finding cannot mask another. The positive controls must pass
under the identical pinned tool and check flags.

| Harness | Expected result | Detector category |
| --- | --- | --- |
| `positive_initialized_read` | pass | ordinary initialized scalar read |
| `positive_valid_bool_pointer_read` | pass | aligned, initialized, valid-value pointer read |
| `negative_uninitialized_i32_read` | fail | uninitialized-memory check |
| `negative_invalid_bool_read` | fail | valid-value check |
| `negative_misaligned_u32_read` | fail | alignment check on a live allocation |
| `negative_null_u32_read` | fail | invalid/null pointer dereference check |
| `negative_immutable_static_write` | fail | write through a pointer to immutable static storage |

Enable the target checks while retaining Kani defaults:

```text
-Z uninit-checks -Z valid-value-checks -Z unstable-options --extra-pointer-checks
```

The pinned Kani revision is `152c6a8c875d9886a67e229247b4826d6105ccfd`
(0.67.0, from `tool_config/kani-version.toml`). In that source,
`kani_metadata/src/unstable.rs` defines `UninitChecks` and `ValidValueChecks`,
documents their behavior, and serializes unstable feature names as kebab-case;
this confirms `-Z uninit-checks` and `-Z valid-value-checks`. The compiler
argument enum in `kani-compiler/src/args.rs` maps its `Uninit` and `Validity`
checks to instrumentation. In particular, validity checks exclude
uninitialized values, so both flags are needed for the intended controls.
`kani-compiler/src/kani_middle/transform/check_uninit/mod.rs` documents the
uninitialized-memory instrumentation and emits the diagnostic
`Undefined Behavior: Reading from an uninitialized pointer of type ...`;
`kani-compiler/src/kani_middle/transform/check_values.rs` documents checks for
invalid values generated by unsafe operations. The CLI declaration in
`kani-driver/src/args/mod.rs` describes `--extra-pointer-checks` as checking
invalid pointers in relation operations and pointer-arithmetic overflow; it
requires `-Z unstable-options` and may produce false counterexamples. Thus the
flag is recorded as part of the pointer-check configuration, while expected
alignment/null findings must be identified from the actual verifier diagnostic.

Accept a negative-control result as detector evidence only when it is a
verifier finding for that harness and matches the intended category. A syntax
or unsupported-operation diagnostic, frontend/compiler error, failed unwind
assertion, timeout, or infrastructure failure is inconclusive. If a control
passes, record that detector/category as missing in this Kani configuration;
do not weaken the control, add assumptions, suppress checks, or claim coverage.
In particular, determine whether the runner's `--no-assert-contracts` changes
the detector path from the emitted diagnostics. If it does, report the exact
missing detector and keep the flag behavior unchanged for this experiment.

The future sorting safety harness should use bounded i32 storage and the real
`insertion_sort_shift_left` without loop invariants. That is a separate
experiment; these controls provide no sorting evidence. Keep all default
checks enabled and report the control results before attributing UB coverage to
the sorting harness.

## Actions suite runner

`ub_detector_controls` invokes `run-ub-controls.sh` on a hosted Linux runner.
Two positive controls require 2/2 covers each before five negative controls run
serially. A single requested budget includes the cold build and all stages;
per-control GNU time records separate stage costs. The classifier preserves
actual property IDs and only counts a negative as detected when Kani finishes
one failed harness and every failed property matches the intended category.
Unreachable unsupported checks are allowed; failed unsupported checks, compiler
errors, unwind failures and incomplete output are inconclusive. Expected
negative failures do not stop the other detector measurements. Run37394356873 at6e0503f completed; see measured results below.

## Actual insertion safety follow-up

Prepared selection `insertion_ub_safety_4` uses `run-insertion-ub.sh` and the
existing four-cell i32 safety harness on actual `insertion_sort_shift_left`.
It injects no loop annotations and supplies a fresh arbitrary comparator result
on every call. Only valid length/offset assumptions apply, with unwind6 and
all unwind assertions retained. The same detector flags apply. Acceptance
requires exactly one verified harness, all7/7 covers, no failed or undetermined
checks, no failed unsupported checks or argument-substitution diagnostics.
Interpret any result together with the independently measured detector gaps;
this bounded nonpanicking i32 proof cannot establish arbitrary lengths, generic
ownership, comparator unwind or unmeasured UB categories. Not dispatched yet.

## Measured results

Run [37394356873](https://github.com/Tiramisu-Cake/verify-rust-std/actions/runs/37394356873)
at `6e0503febfe9c162e2e89a7ccfbd6126c9ca3be9` ran every control with the
pinned configuration. Both positive controls passed all2/2covers. The uninit,
invalid-bool and alignment controls had exactly their intended failures. NULL
read failed `pointer_dereference.1` (pointer NULL), plus uninitialized-pointer
and outside-object-bounds properties; the conservative classifier kept it
inconclusive because of those collateral findings. Immutable static write
passed192checks,19 unreachable: this concrete mutation was not rejected.
The suite correctly returns1/notvalidated. Do not equate failure of that whole
suite with absence of the three positively measured detectors, or attribute
immutable-byte coverage to a future green SmallSort harness. No detector
flags or control behavior have been weakened. See README for costs and hashes.

## Observed immutable-store diagnostic

Prepared manual selection `ub_immutable_observation` runs the same two positive
controls, then a separate `negative_immutable_static_write_observed` harness.
The original write-only reproducer remains unchanged. The new control performs
the same write, then a volatile read, an assertion of9 and a cover of9. A green
negative harness with1/1cover confirms a modeled observable store while exposing
the missing immutability detector; the suite must still fail. Assertion failure,
unsupported volatile operation or missing cover is inconclusive, and must not
be counted as an immutable-byte check. It has not run yet.

Pinned-source audit finds pointer-validity checks for ptr::write, but no emitted
mutable-storage property in the first control. The store call has202 VCCs
(46 after simplification), and its pointer/write checks pass. Kani tags static
const symbols in operand.rs/goto_ctx.rs; the inspected CBMC6.10.0 source has no
consumer found for that metadata. This is evidence of a model gap, with emitted
GOTO-symbol details still uninspected. --no-assert-contracts controls contract
closure assertions and ptr::write has no such Kani contract here; regular UB
and pointer instrumentation remains active.
