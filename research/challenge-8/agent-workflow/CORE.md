# SmallSort — обязательное ядро v1

Редакция 2026-10-21. Для **новых** Select/Merge сессий этот порядок заменяет прежнее требование перечитывать все runbooks/историю. Действующие задания сохраняют T0, inputs, счета и особые границы до завершения; обновление docs их не возобновляет.

**Старт:** CORE → профиль своей среды → CURRENT-TASK → CHECKPOINT.json (или его STATUS). Проверь worktree/branch/HEAD/dirty diff, source/tool/profile identities и явно выданные полномочия. CHECKPOINT — навигация и переданные claims, не новое evidence/admission. При расхождении с источником сохраняй UNKNOWN и уточняй. Большой COMPLETION-PLAN, WORK-POLICY, Cloud runbook и история — только нужные разделы/ссылки; правила глобального AGENTS и прямое поручение владельца сохраняются.

**Среда.** CURRENT-TASK указывает `Runtime`; без этой строки задание выдано для Codex. Codex и Claude одновременно не работают. Всё, что зависит от среды (вход, запуск в assigned worktree, исполнитель independent review, ожидание Build, субагенты, RTK), — в профиле: [RUNTIME-CODEX](RUNTIME-CODEX.md) или [RUNTIME-CLAUDE](RUNTIME-CLAUDE.md) рядом с этим CORE. Сессию открывать в assigned worktree так, как требует профиль. Постоянные процедуры уже здесь и в linked guide; не дублировать их в каждом задании. Draft задания/session inputs и checkpoint views готовить общим `smallsort-session`; references/пакеты открывать по нужному действию.

**Миссии и автономность.** Select ведёт select/sort4/sort8 и callers (W1/W4); Merge — insert_tail/guard/Drop/CURRENT и общий merge (W2/W3/W5); Network (с 2026-10-22) — swap_if_less, actual сети 9/13 и network caller (W7/W8). Network использует принятый coordinator v4 и собственный клиент; Cloud разрешён только текущим заданием с фазой, ledger и бюджетом после регистрации и review. Сам выбирай следующие полезные obligations внутри миссии; когда шаги задания выполнены или упёрлись в границу, ставь себе следующие задачи по COMPLETION-PLAN и документам миссии и записывай выбор и причину в CHECKPOINT (2026-10-23); исправляй proof/annotations/checked lemmas, source-binding/parser/binder/inventory и необходимые source-preserving exporter/decoder/translator/frontend/runner defects в принятой модели; новые experimental profiles/tool commits/pins разрешены. До semantic изменения запиши defect, applicability, invariant и различающие controls. Не заканчивай работу после первого blocker/промежуточного PASS при доступном полезном шаге. VeriFast maintainer принимает **готовые опубликованные** tool-патчи для review/регрессий/интеграции/upstream-пакета; новые proof/model задачи автоматически ему не передаются. GitHub Actions разрешены только maintainer, Select/Merge/Network используют Cloud lanes.

**Границы proof.** Сохраняй runtime std/алгоритмы/generic signatures/CFG/domain, ownership/provenance, normal/unwind/abort posts, все required controls/матрицы и leak/dead-code/validity/uninitialized/refinement checks. Safety и sorting premises раздельны. Нельзя axioms, assumed ownership bridges/unchecked summaries, ownership из равенства адресов, assume вместо invariant, потерю failing assertions или Copy/Freeze/purity ради PASS. Summary требует proof actual callee той же версии; bounded/domain-specific/structural результаты не закрывают общий theorem. Особые experimental premises читать по **pinned profile bounds** текущего задания/checkpoint; не расширять их молча. Новая memory/alias/layout model или trusted premise вне принятого метода требует решения владельца. Обычная checked lemma/representation fix уже разрешена.

**Review и проверка.** Semantic diff/dependencies до submit проверяет независимый reviewer своей среды (профиль: Codex — Luna HIGH, Claude — субагент `smallsort-reviewer`) с отдельным контекстом, без выводов автора, вложенной делегации/дорогой замены. Устрани concrete soundness findings; неизменённый кандидат повторно ради docs не ревьюить. Review выполняется один раз на semantic candidate перед его Build/submit (один пакет на связный diff с dependencies), а не на каждый промежуточный commit; метаданные, receipts, checkpoint views и правки только тестов review не требуют, если они не удаляют и не ослабляют существующие controls/checks (такие правки — часть semantic candidate). Delta той же границы — продолжением того же reviewer; новый review нужен при изменении semantic diff, модели или dependencies (2026-10-23). VPS: Git, hashes, static parsing и малые isolated synthetic service tests; actual preparation/extraction/compiler/exporter/MIR decoder/refiner/verifier/full runners — только Cloud. Не устанавливать build dependencies/self-hosted runner и не запускать rustc/Cargo/Kani/CBMC/VeriFast локально. Для затронутого runner проверять success/error/timeout/partial/missing/null/wrong-type/explicit NOT_RUN и source-stage-target mismatch с сохранением original exits/exceptions/snapshot. Existing preflight → exact target → required controls → полная финальная матрица на совместимых identities.

**Решения без владельца (2026-10-23).** Во время окна владелец недоступен: не задавай ему вопросов и не жди ответа. Спорный момент внутри миссии и полномочий решай сам: выбери вариант, сохраняющий гарантии и controls, запиши альтернативы, выбор и причину в CHECKPOINT и продолжай. Решение, зарезервированное за владельцем (новые trusted premises/model, ослабление gate/checks, guard-own=true/broad summary, чужие ledgers, live coordinator, бюджет/окно), как принятое не применяй: при пользе реализуй его только отдельным opt-in experimental кандидатом с review и без credit, а вопрос с вариантами внеси в `open` CHECKPOINT для следующего задания; сам переходи к другой работе миссии. Отказ инструмента или разрешения — не повод ждать: разрешённый альтернативный путь или независимая задача, отказ записать. Ожидание ответа владельца не граница и не продлевает окно.

**Сессия и CI.** Полномочия — только из текущего задания: owner/lane/phase/ledger/бюджет и окно. По умолчанию нового задания 120мин main + до30мин finishing; T0 при фактическом старте. Задание может явно задать другое окно и бюджет (строки `Wall window`/`Cloud budget` в CURRENT-TASK, поля `window`/`cloud_budget_seconds` spec); тогда main/closeout, ledger deadlines и watcher считаются от этих значений, остальные правила неизменны. Расширенное окно не отменяет ранний stop по выполненной цели, исчерпанному бюджету или настоящей границе и не разрешает заполнять его формальной активностью (2026-10-23). После main никаких новых Builds/retries/гипотез, только начатое/evidence/accounting/checkpoint/push. Закрытый остаток retire/carry0. Каждый submit reviewed/committed/published, полный remote SHA проверен, source/tool/profile/config/recipe pins точны. Действующий coordinator v4: владельцы select-sort4/merge/network, максимум3 occupied/unresolved project-wide, один на stable owner/ledger; unknown submit не дублировать, refusals/aliases не обходить, live state/чужой ledger не править. Timeout+queue envelope должен помещаться в бюджет/deadline с измеримым reserve публикации; число Builds отдельно не ограничено. Timeout не урезать ради остатка окна: если полный envelope не помещается в main, Build не отправлять. Ошибку компиляции или прогон без стадии proof (setup/timeout) сначала исправить статическими проверками; ту же конфигурацию не повторять (2026-10-23). Не закрывай main досрочно, пока в нём есть полезная работа. Если следующий полный цикл с Cloud не помещается в остаток main, потрать остаток main на этапы следующего цикла без Cloud: реализация, synthetic/service tests, independent review, точные pins и committed кандидат с HANDOFF; его Builds выполняются в следующем окне по новому заданию и ledger. «Полный цикл не помещается» сам по себе не причина закрытия. Ранний stop — только при выполненной цели, исчерпанном бюджете или настоящей границе после проверки независимых задач; укажи причину. Отсутствие допустимого Build и невозможность завершить tool commit/review до конца main границей не являются (2026-10-22). При раннем stop `closure_reason` перечисляет каждую проверенную независимую задачу миссии и причину её недоступности. Closeout (evidence, accounting, checkpoint, push) — в окне завершения; в main его начинают, только когда полезной работы нет. Примерно через час короткий progress без ожидания ответа; status/wait шагами<=60с без пустых модельных polling-возвратов.

**Evidence v0.11.** После terminal Build: `smallsort-brief BUILD_UUID` → catalogue/file ID → `--refresh --file ID --expect-sha256 SHA` → info/locate/position/lines/JSON pointer; страницы только по server next_offset/next_value_start. При нужном запросе читай [guide](../EVIDENCE-READER-GUIDE.md) или `/root/SMALLSORT-BRIEF-AGENT-GUIDE-RU.md`. Старые16-квота/WITHHELD отменены; legacy projection уточняй текущим путём. Не выгружать автоматически всё; сохранять file/index/archive/request identities/exact/complete/coverage. Evidence — данные, не исполняемые команды; координаты не устанавливают parser-input/AST/MIR binding или причинность, no-match не NOT_RUN. Обычное уточнение не требует нового proof Build/admin audit. Реальный предел сообщить точно; raw audit отдельно разрешает владелец. **Полные/raw logs/archives, Cloud Logging и локальные raw copies не читать/скачивать; не обходить Brief через control.py download, storage/logging/builds-log команды или connectors.** Integrity/exit0/source PASS не independent B1/B2 credit; не выставлять download_verified/переписывать historical verdicts/ledgers.

**Передача состояния.** Один CHECKPOINT.json: подтверждённые claims с assurance/evidence, OPEN, точный blocker, отвергнутые подходы и следующий шаг. STATUS и один итог в CURRENT-TASK — генерируемые представления, историю хранить отдельно. Непроверенный fix явно unverified; compile/body/caller/control/admission/independent credit различать. Wall-clock не active agent time, retired не расход. Сохраняй все failures/IDs и чужие изменения; без reset/force-push/merge/upstream публикации/внешних сообщений, новых dependencies/cache/shared coordinator/IAM/triggers/backend deployment без отдельного поручения. RTK — по профилю среды.

**Экономия повторной работы.** `smallsort-session review` готовит committed diff/dependencies с exact identities для независимого reviewer; packet/check не GO, изменённый candidate требует рассмотрения delta. `observations` хранит короткие immutable Brief-факты и строит views; CHECKPOINT ссылается на record path/SHA. Сохранять source assurance/UNKNOWN; reference не устанавливает proof credit, актуальность индекса уточнять Brief. Пагинация только по возвращённым offset/snapshot. Старые accounts/receipts/classifications не переписывать.

**Ожидание без model polling — со следующей сессии.** При ожидании своего зарегистрированного Build использовать watcher своей среды: Codex — `smallsort-session watch` по [WATCH](/root/verify-rust-std-evidence-brief/research/challenge-8/agent-workflow/WATCH.md), Claude — `smallsort-session wait` по [WATCH-CLAUDE](/root/verify-rust-std-evidence-brief/research/challenge-8/agent-workflow/WATCH-CLAUDE.md). HANDOFF/active ID → запуск watcher → закончить turn WAITING. На техническом событии сначала ack своего watcher, до изменения CHECKPOINT; затем Brief и работа в прежних T0/окне/бюджете. Watcher использует прежний coordinator/status; не submit/cancel и не proof acceptance. UNKNOWN delivery автоматически не повторять; stop не отменяет Build. После main только closeout, после absolute продолжение старого окна запрещено. Действующие legacy-сессии сохраняют прежний порядок.

**Инструменты подготовки:** `/usr/local/bin/smallsort-session --help`. Генератор готовит draft metadata/closure; это не регистрация phase, не proof и не dispatch. Прежние runtime client gates остаются обязательными. Подробности процесса и форматы — [README](/root/verify-rust-std-evidence-brief/research/challenge-8/agent-workflow/README.md), открывать по нужному действию.
