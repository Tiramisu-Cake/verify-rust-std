# R17 hosted profile admission design — 2026-10-21

The first R17 hosted one-cell attempt was refused before the campaign because the R11 runner still equated `effective_tool_commit` with the historical `guard_return_trace_tool_commit`. That rule admits the captured R11 profile but rejects the reviewed R17 refiner candidate, even though R17 intentionally leaves the historical trace-tool pin unchanged. The R11 source-pin loop also treats `refiner_core_source_sha256` as immutable, while R17's approved extension changes that one source pin.

Admission is limited to the exact committed R17 baseline bytes (SHA-256 `eb61e49397cd9973ec12d1675bd8bd4867c7374de22e7c1c6a8a58e991266375`) and the exact R17 registration record. Relative to that baseline, only `r17_registration` may be added and only `effective_tool_commit`, `refiner_core_source_sha256`, `guard_return_trace_patch_sha256`, and the final SHA in `ordered_patch_chain` may change. The chain remains length 19, preserves entries 1–18 byte-for-byte as decoded JSON, and retains the final patch path. The historical `guard_return_trace_tool_commit` remains pinned to the captured R11 tool. All other profile values remain equal to baseline.

The legacy R11 route remains unchanged when no R17 registration key exists. A present but malformed, partial, or unknown registration fails closed. Once the narrow extension is admitted, the existing profile-build receipt, source build, schema, source pins, generated binary identity, provider receipt, and source applicability checks continue to run; only the R17 refiner-core source pin and effective tool identity receive their exact registered values. Tests use only in-memory JSON and committed profile bytes and do not invoke a compiler, verifier, or hosted build.
