# MIR OR join admission controls — separate diagnostic driver

The pinned console exports MIR internally; it has no documented input-MIR CLI.
Source mutations would fail exact source admission before reaching the new
matcher. Therefore the proposed controls use a separate disposable tool copy
with a diagnostic exporter wrapper. Production six/seven homes and profiles
retain the unchanged official exporter. This driver is not an accepted proof
profile or a new compiler/model semantic rule.

The wrapper must call the exact official exporter with its original arguments,
preserve its stderr/exit, capture normal-mode Capnp output and encode only a
single schema-valid deliberate mutation after a lossless positive roundtrip.
Raw stdout, decoded text, encoded message, commands/status, exporter/schema/
wrapper hashes and the exact one-field mutation certificate are published.
The decoded normal message must contain exactly the actual pinned
bidirectional_merge body and source; readonly MIR is forbidden. The first
control changes one StorageDead to StorageLive in join block34, with the same
local and statement count. A second changes a Goto target to the existing block38.
Any malformed message, wrong source/body, failed decode/encode, extra mutation,
export failure or unexpected frontend error is INCONCLUSIVE.

Trust assumptions: capnp schema/encoder are the existing pinned Cloud tools;
the unchanged Rust exporter creates the original normal message. The wrapper
only creates deliberate diagnostic inputs; it supplies no permissions, axioms,
proof summaries or production code. Ordinary annotations/source/model/console
are unchanged in the separate copy. The driver must rehash production tool homes
before and after, and compare every copied tool except the explicit wrapper.

Expected stage is frontend admission with the exact new
MIR-OR-JOIN-LIVENESS refusal, before target body verification. This is an
admission negative, never a proof-negative. A positive unmodified normal roundtrip
must produce the actual frontend AST with both Gotos/panic; a short diagnostic
proof timeout cannot be credited as actual theorem PASS. The actual positive
full-post proof uses the production seven console/exporter, separately.

This remains an UNTESTED draft until a fresh Cloud run. More shape controls,
proof-negative live/dead fixtures and full relevant profile gates remain required.
An independent driver gate does not resolve experimental kernel/cleanup trust.

## Draft driver and its exact input boundary

`control-driver.py` and `control-exporter.py` implement this as a separate
Cloud-only diagnostic in a third tool home; the production six/seven tools
and semantic patch are unchanged. The main runner/audit integrate an optional
bounded diagnostic group and the pin manifest binds both driver files. The driver takes the exact prepared
`bidirectional_merge_len23` case, its preflight record, the **production
seven** actual case's `normal-exporter.out` and normal-mode provenance, both
production tool homes, the seven build manifest, pinned schema and compiler
sysroot. It refuses until the main OR manifest has a fresh admitted source
hash and locations. The main run integrates a separately bounded call after the actual proof;
these files do not dispatch a Build by themselves.

The driver copies the seventh home's `bin` tree to a fresh disposable tool
home, moves the copied official exporter to a sibling `.official` file, then
installs only the diagnostic wrapper at the exporter path. It records every
copied bin entry before installation and rehashes the entire bin inventories
of the six/seven production homes before and after. It also rehashes their
kernel, translator and parser sources. The test home has the same bin entries
except for its explicit wrapper and preserved `.official` copy. The wrapper
requires the normal exporter command, exact source hash, official exporter,
schema/parser hashes and byte-identical official normal Capnp output to the
production seven capture. A readonly export cannot enter the control.
The provider overlay changes the working-tree admission helper, so the
driver extracts the exact pre-overlay `stack-address-admission.py` parser
blob from the Cloud checkout's `PROOF_SHA` into private evidence, requires
its known SHA-256, and gives only that private parser to the wrapper. It
records the current overlaid helper's distinct hash; no overlay change is
silently accepted as the diagnostic message parser.

For each mode, the wrapper stores the unchanged official stdout/stderr/status,
normal decoded text, textual message passed to `capnp encode`, encoded binary,
redecoded text and a JSON certificate. The positive mode requires byte-equal
**decoded text** before and after re-encoding; the encoded binary hash is
recorded but is not required to equal the official binary representation.
For negatives, a full-consumption decoded-tree comparison must equal the
official tree except the named one-field StorageDead-to-StorageLive or Goto
target mutation. The manually captured diagnostic message and the one
actually consumed by the frontend must have equal certified encoded-message
hashes.

The driver runs the seventh console in the disposable tool copy with the
unchanged full prepared Rust case. Its `roundtrip` outcome is
`ADMISSION_PASS_ONLY` only if the dumped target proof AST contains the two
actual Goto37 nodes and one panic body call. The two mutations are
`EXPECTED_FRONTEND_REFUSAL` only at the exact new matcher error at the
admitted signature line, with verifier exit 1 and no target-body execution.
All other results are `INCONCLUSIVE`. All modes and the aggregate retain
`accepted=false`, including a short verifier timeout after positive AST
admission. Each copied source pair also runs the unchanged official
refinement checker through the production seven home; its failure is
inconclusive. The MIR mutation is never given to the refiner and is not a
runtime Rust source change. The driver's work cap is at most 180 seconds; no proof PASS or
actual-source theorem can be inferred from its result.

This driver has only static review. Capnp text encoder behavior, exact
frontend exporter invocation, fresh BB numbering, AST dump order and
refusal formatting still require Cloud calibration. A source, schema or
frontend mismatch is setup/inconclusive evidence, not a successful negative.
